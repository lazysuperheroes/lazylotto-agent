## Critical findings (2 deduped)

### R12-FG-1 (C / bug) — `force_release` writer drops `userId` + `tokenReservations`; Phase-9 Cluster B's heldByToken decrement is dead code on production topics
**Convergent confirms:** P5-001, P10-004, P1-003 (3 personas).
**Site:** `app/api/admin/uncertain-tx/[id]/force-release/route.ts:427-434`.
**Bug:** The only production writer of the `force_release` control event:
```ts
await accounting.recordControlEvent('force_release', {
  by: auth.accountId,
  reason,
  uncertainTxId: id,
  kind: entry.kind,
  mirrorResult,
  idempotencyKey: `force-release:${id}:${fenceTs}`,
});
```
No `userId`. No `tokenReservations`. Phase-9 Cluster B's reducer-side fix at `verify-audit.ts:874-884` is gated by `if (event.userId && event.tokenReservations)` — on every real production event, that guard is false. `heldByToken` is **never** decremented. The R10-FG-16 false-positive `user_balance_negative` alert that Phase-9 was supposed to retire still fires the moment any operator force-releases a triaged play. **The Cluster B closure is decorative for the load-bearing operator path.**
**Compare to:** `handlers.ts:807` (`play_uncertain_success_pending_triage` writer) which correctly threads `userId: details.userId, tokenReservations: details.tokenReservations`. The pattern exists; the force_release writer just doesn't follow it.
**Phase-9.5 fix:** read userId + tokenReservations from the dead-letter entry's `details` field, pass them in. Plus a regression test asserting the synthetic two-event sequence (`play_uncertain_success_pending_triage` + `force_release`) ends with `heldByToken === 0`.
**Estimate:** ~30 LOC + ~80 LOC test.

### R12-FG-2 (C / bug) — `MultiUserAgent.playForUser` re-saves stale `user` AFTER `lastPlayedAt` update; second saveUser reverts the first
**Convergent confirms:** P10-001 (1 persona, airtight evidence).
**Site:** `src/custodial/MultiUserAgent.ts:736` then `:874`.
**Bug:** Phase-9 Cluster C correctly replaced the `user.lastPlayedAt = ...` mutation at line 736 with `saveUser({...user, lastPlayedAt: new Date().toISOString()})`. But line 874, in the same `playForUser` body, then calls `this.store.saveUser(user)` — passing the ORIGINAL `Readonly<UserAccount>` snapshot bound at line 534. **That second write OVERWRITES the cache entry just persisted at line 736, reverting `lastPlayedAt` to its pre-play value.** `saveUser(user: UserAccount)` accepts a Readonly via TS structural subtyping, so no compile error caught it. The Phase-9 commit body claims "Both replaced with saveUser of fresh objects" but the second saveUser is unchanged.
**User-visible failure:** every successful play resets the `lastPlayedAt` indicator on the dashboard. Activity tracking, idle-disconnect, and strategy-cooldown logic that reads `lastPlayedAt` see a wrong value.
**Phase-9.5 fix:** capture the post-saveUser fresh user object at line 736 and pass IT to the second saveUser at line 874 (or re-fetch via `store.getUser(userId)`). Plus a regression test asserting `lastPlayedAt > pre-play timestamp` post-`playForUser`.
**Estimate:** ~10 LOC + ~40 LOC test.

## High findings (3 deduped)

### R12-FG-3 (H / bug) — `IStore.getOperator()` not Readonly; sibling archetype to R10-FG-2 NOT closed
**Convergent confirms:** P10-002 (1 persona).
**Site:** `src/custodial/IStore.ts:152` and consumers at `src/custodial/MultiUserAgent.ts:2046`, `app/api/admin/overview/route.ts:58`.
**Bug:** The Cluster C migration made `getUser*` return `Readonly<UserAccount>` to catch top-level mutation of the store cache. But `getOperator(): OperatorState` was left mutable. `RedisStore.getOperator` at `RedisStore.ts:566` returns `this.operator` by reference (no clone). Any caller doing `op.balances[token] = ...` mutates the live cache. OperatorState carries `balances`, `totalRakeCollected`, `totalGasSpent` — all balance-conservation-critical.
**Phase-9.5 fix:** `getOperator(): Readonly<OperatorState>` + `getAllUsers` already typed; cascade through callers. Mutations route through `updateOperator(updater)` (already the controlled write path).
**Estimate:** ~15 LOC.

### R12-FG-4 (H / bug) — `parseRefund` "5 reasons" is actually 4 + multi-cause silent attribution
**Convergent confirms:** P1-001 (1 persona).
**Site:** `src/custodial/hcs20-reader.ts:1591-1592` (parseRefund); `:660-674` (dispatcher).
**Bug:** Phase-9 Cluster B's commit body and the dissection §6 both promised discrimination of "FIVE distinct null-return reasons" via `return null | { reason: ... }`. The shipped implementation has FOUR reasons + a silent fall-through, AND the dispatcher re-derives categorization from the raw payload OUTSIDE `parseRefund` (instead of the dissection's prescribed tagged-union return). Two consequences:
- A refund with both `from===''` AND `refundTxId===''` increments `refundsDroppedMissingParty` only; the missing-refundTx counter stays at 0. Per-counter conservation arithmetic is wrong.
- If `parseRefund` ever grows a 6th reason, it falls through ALL FOUR dispatcher branches → `skippedMessages++` only, no alert fires → R11-FG-1 over-credit signature reappears.
**Phase-9.5 fix:** refactor `parseRefund` to return `NormalizedRefundEvent | { reason: 'empty-original' | 'missing-from' | 'missing-to' | 'invalid-amt' | 'missing-refund-tx' }` per the dissection's literal spec. Dispatcher takes the tagged reason directly; future 6th reason becomes a TypeScript error not a silent skip.
**Estimate:** ~50 LOC.

### R12-FG-5 (H / bug) — `structural-gate` is the new placebo escape hatch
**Convergent confirms:** P8-001 (1 persona, airtight evidence).
**Sites:** `src/__tests__/audit-coverage-scan.ts:98` (schema), `src/__tests__/audit-coverage.test.ts:130, 182` (gates).
**Bug:** R11-FG-2 closure struck `documentation-only`, but the `structural-gate` exemption is now wider than `'individual'`. Three holes compound:
1. **Schema:** `tests: z.array(TestRefSchema)` has no `.min(1)`. Docstring claims "every entry MUST link at least one test or a structural fixture"; schema doesn't enforce it.
2. **Annotation cross-check** at `audit-coverage.test.ts:130` skips `structural-gate` entries entirely.
3. **Placebo gate** at line 182 filters ONLY `coverageStrategy === 'individual' && tests.length === 0`.

**Constructive bypass:** any future entry with `coverageStrategy:'structural-gate'` and `tests:[]` passes every gate vacuously. Same Goodhart escape as R11-FG-2, one label deeper. The audit-machinery-audits-itself archetype recurs.
**Phase-9.5 fix:** add `.min(1)` to the `tests` Zod array AND a dedicated `it()` block asserting `structural-gate` entries' linked tests resolve to a recognized structural fixture (`sibling-archetype-gate.test.ts`, `claim-archetype-gate.test.ts`, `audit-coverage.test.ts`).
**Estimate:** ~25 LOC.

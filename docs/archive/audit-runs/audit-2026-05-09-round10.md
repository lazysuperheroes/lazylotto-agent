## Four NEW Phase-7 introduction bugs (CRITICAL)

### `[ ]` R10-FG-1 (C) — pendingLedger SADD-after-flush race re-introduces R9-FG-6 archetype
**Convergent confirms:** P1-001, P2-001, P5-001 (3 independent agents).
**Bug:** `src/custodial/pendingLedger.ts:287-312` (eager) and `:499-508` (periodic). Order is `flush() → SADD → LREM`. A Lambda kill between `await store.flush()` and `await redis.sadd(...)` leaves the user balance debited but no applied-set record. Next drain: `SISMEMBER` → 0 → re-mutates → **double-debit**. The author's own comment at lines 296-308 recommends SADD before flush, but the code does the opposite. R9-FG-6 was NOT actually closed — the window narrowed from 7 days to ~1 round-trip but the archetype is intact.
**Fix:** Either (a) SADD before flush + tolerate-on-flush-fail, or (b) pipeline `flush + SADD` via Redis MULTI for atomicity, or (c) make body fully idempotent on the store side (per-row sourceTx applied-set inside the JSON blob the store flushes).

### `[ ]` R10-FG-2 (C) — `/api/user/status` mutates store-cached user object → phantom DEFICITS in withdraw path
**Convergent confirms:** P1-002 (1 agent, airtight evidence).
**Bug:** `app/api/user/status/route.ts:140-155`. `user` is a live reference returned by `store.getUser(userId)`. Line 154 reassigns `user.balances = adjustedBalances`, mutating the cached store object. Comment at line 137 explicitly says "we don't mutate the store-cached object" — but the code does. Subsequent reads on the same warm Lambda — including the SAME user's `/api/user/withdraw` — see balances already net of pending. Withdraw then applies its own pending-debit logic on top → **double-deducting**. Pre-Phase-7 was phantom funds; Phase-7 fixed that but introduced phantom DEFICITS.
**Fix:** Build a separate response object: don't reassign `user.balances`; spread `{ ...user, balances: adjustedBalances }` into the JSON response body.

### `[ ]` R10-FG-3 (C) — `parseRefund` silent null on empty `originalDepositTxId` over-counts user balance
**Convergent confirms:** P1-003, P5-004, P12-001 (3 independent agents).
**Bug:** `hcs20-reader.ts:1542` returns `null` when `originalDepositTxId` is empty. The dispatcher increments `skippedMessages++` but emits NO categorized signal. Verify-audit's reconstruction now misses the refund entirely → user's `totalRefundedByToken[token]` is short → reconstructed balance OVER-credits the user. **Inverse failure to pre-Phase-7**: pre-fix double-counted via truthy gate bypass; post-fix drops the event. Both regimes break invariant 3. Plus: breaks the CLAUDE.md "v1 batch dual-shape fallback" contract for legacy testnet refund anchors.
**Fix:** Emit a categorized stat + alert. Either (a) emit the event with `originalDepositTxId: '<legacy-empty>'` sentinel and skip dedup, or (b) emit critical alert from the dispatcher when `parseRefund` returns null while the message had `op === 'refund'`.

### `[ ]` R10-FG-4 (C) — Manifest `tests:[]` + `coverageStrategy:'individual'` placebo-by-elision
**Convergent confirms:** P8-001, P10-001 (2 agents). 8th recurrence of R2-FG-0 archetype.
**Bug:** `src/__tests__/audit-coverage.test.ts:122-147` annotation cross-check loops `for (const ref of f.tests)`. Empty array → no iteration → vacuous pass. **9 of 12 R9-FG entries** (R9-FG-1, 2, 3, 4, 6, 8, 11, 12, 13) ship with `coverageStrategy:'individual'` AND `tests:[]`. **Five are CRITICAL severity.** Phase-3's R8-FG-12 fix introduced `coverageStrategy` precisely so `'documentation-only'` could waive testing — but `'individual'` was meant to enforce per-finding tests. Goodhart-the-default: strict setting defeated by the empty-tests escape hatch. The exact archetype Phase-3 was created to prevent.
**Fix:** Add a Zod refine OR a separate gate test:
```ts
it('individual-strategy entries declare at least one test', () => {
  const empty = manifest.findings.filter(
    (f) => f.coverageStrategy === 'individual' && f.tests.length === 0,
  );
  assert.equal(empty.length, 0, ...);
});
```

### `[ ]` R10-FG-12 (H) — velocity counter inflation creates legitimate-user 24h DoS lockout

### `[ ]` R10-FG-13 (H) — `.message.startsWith(...)` archetype undefended by widened gate
**Convergent confirms:** P3-001 (1 agent, live hits).

### `[ ]` R10-FG-15 (H) — eager-path flush failure swallowed via `.catch(warn)` then proceeds
**Convergent confirms:** P5-002 (1 agent).
`pendingLedger.ts:287-294`. If flush fails (Redis blip), the warn fires but execution continues to SADD + LREM. Mutation didn't reach Redis, applied-set + LREM both succeed → **debit silently lost forever**. Strictly worse than periodic path which awaits flush bare.
**Fix:** Drop the `.catch` swallow on the eager path. Let flush throw; fencedClaim's catch releases the claim, row stays, next drain retries.

### `[ ]` R10-FG-16 (H) — `heldByToken` no decrement on `prize_recovery` events → false-positive negative-balance alerts

## Convergence verdict

**The audit cycle is NOT converging.** The user's stated bar:
- ≤20 findings: ship Phase 7, garbage-collect audit docs.
- ≥30 with new criticals: stop, dissect with `/fb:how`, design Phase 8 around the new pattern.

**R10 lands at ~50 unique findings with 4 NEW Phase-7 introduction criticals.** We hit the second bar.

The pattern across rounds:
- **R6 → R8**: 115 → 32. Big drop. R7 structural fixes worked.
- **R8 → R9**: 32 → 45. Slight increase. Phase 6 introduced 2 wire-only closures (heldByToken not subtracted, depositCreditFlushOrphanedByToken not subtracted).
- **R9 → R10**: 45 → 50. Roughly flat. Phase 7 introduced 4 new Phase-7-style criticals:
  1. SADD-after-flush race (the very R9-FG-6 it claimed to close).
  2. user-status route mutates store cache (phantom DEFICITS replacing phantom funds).
  3. parseRefund silent null drop (inverse of pre-Phase-7 over-counting).
  4. manifest `tests:[]` placebo-by-elision (Phase-3 archetype recurrence).

**Each phase ships with its own introduction-bug archetype.** R7 closed all of R6's. Phase 6 introduced "wire-only closures" (data captured but not used). Phase 7 introduced "comment-vs-code mismatches" (the SADD ordering, the user.balances mutation contradicting its own comment, parseRefund's null silently changing failure-mode direction).

The structural fixes ARE landing — every R9 critical is CLOSED at the named site. But the work introduces NEW criticals proportional to the surface changed. The audit cycle is converging on **bug-introduction RATE**, not bug-COUNT.

**Recommendation per the user's "stop and dissect" rule: STOP. Run `/fb:how` to dissect why each phase introduces ~4 new criticals despite the structural-fix discipline.** The likely root cause: large mechanical refactors (whole-file gate scan, schema split, SADD primitive, mapErrorToResponse) ship without behavioral integration tests — every commit is reviewed by tests that would have caught the prior round's archetype, not the current round's introduction archetype.

If the user opts to push forward, **Phase 8 must close R10-FG-1..4 first** (the 4 new criticals) before any other work — they directly contradict the structural fixes that shipped in Phase 6 and Phase 7.

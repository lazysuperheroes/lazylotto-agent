# P11 performance — Round 11 audit
## Summary: C=0 H=1 M=2 L=2; total 5

Phase-8 closures introduce zero measurable hot-path regressions on their own. The dominant
performance hazard remains a **pre-existing Phase-7 latency multiplier** (R10-FG-11): every
`/api/user/status` poll executes `LRANGE 0 -1` on a global pending-ledger list and decodes
all rows in-process. Phase-8 did not address this; the new `responseBalances` variable rides
on top of that same `LRANGE` call. The other Phase-8 deltas (SADD-before-flush reorder, refund
counter, audit-coverage gate) are within-noise.

## Findings

### P11-001 (high) — `/api/user/status` does global O(N) LRANGE+JSON.parse on every dashboard poll
**Site:** `app/api/user/status/route.ts:132` calling `listPendingLedgerAdjustments()` defined at `src/custodial/pendingLedger.ts:100-120`
**Bug:** The Phase-7 pending-adjustments badge calls `listPendingLedgerAdjustments()` which does `redis.lrange(LIST_KEY, 0, -1)` against a SINGLE GLOBAL LIST (no per-user shard), then JSON.parses every row, then filters by `userId` in JS (`route.ts:133`). Quantification at typical dashboard poll cadence:
  - 1 user, 1 entry: ~3-5ms (one Redis round-trip + parse).
  - 100 users, 5 pending entries each (500-row list), 30s dashboard poll, 100 concurrent dashboards: each poll = 1 LRANGE + 500 JSON.parse calls. JSON.parse of a ~250-byte object ≈ 5-15µs in V8 → 500 × 10µs = ~5ms CPU per request, plus the round-trip. With 100 dashboards polling every 30s = 200 req/min cluster-wide, all reading the SAME 500-row list. Effective CPU: ~1s/min just on JSON.parse-and-filter, all on the hot Lambda path. Network: 200 × ~125KB = 25MB/min Redis egress for the list payload alone.
  - 1000 users, 5 entries each (5000-row list): 50ms parse cost per call, ~1.25MB payload per call. At 200 req/min cluster-wide = 250MB/min Redis egress, ~10s/min CPU.
**Why:** R10-FG-11 (open since Phase-7 Cluster E shipped the pending-debit feature) is a quadratic-ish hazard: list grows with cluster-wide pending volume, and every authenticated dashboard poll scans the entire thing. Phase-8 Cluster C (commit 45372d3) did NOT close this — the change was a defect fix on the response-shaping side (not mutating store cache), and it inherits the same `LRANGE 0 -1` call. The withdraw and play paths also call `applyPendingLedgerForUser` which does its own `LRANGE 0 -1` (`pendingLedger.ts:184`). Mitigation requires sharding the list per-user (e.g., `pending:adjustments:{userId}`) or maintaining a per-user index set — neither shipped in Phase-8.

### P11-002 (medium) — `responseBalances` change adds 1 extra spread + 1 token-map shallow copy per pending-bearing user
**Site:** `app/api/user/status/route.ts:130, 150-167`
**Bug:** Phase-8 changed the previous `user.balances = adjustedBalances` (zero-copy assign) to `let responseBalances = user.balances` followed by, on the pending branch, `{ ...user.balances, tokens: { ...user.balances.tokens } }` plus a per-token `{ ...t, available: ... }`. For a user with K tokens (typical K ≤ 10): ~K+2 object spreads vs. zero before. Cost per request with pending: ≈ 1-3µs of GC + allocations. Without pending: ZERO change (the `let responseBalances = user.balances` aliases the existing reference, no copy). Confirmed: the no-pending path is reference-identity to `user.balances`, no regression.
**Why:** The fix is correct (R10-FG-2 was a real correctness bug — store cache mutation across warm Lambda invocations), and the cost is dominated by P11-001's LRANGE round-trip (~3-5ms), so the spread overhead is <0.1% of the call. Confirmed no measurable regression. Document for completeness.

### P11-003 (medium) — refund-empty-original counter: each refund msg adds one `String(...)` coerce + one truthy check
**Site:** `src/custodial/hcs20-reader.ts:651-654`
**Bug:** Phase-8 added `const orig = String(msg.payload.originalDepositTxId ?? ''); if (!orig) stats.refundsDroppedEmptyOriginal++;` inside the `if (!ev)` skip branch of the v2 refund dispatcher. Quantification:
  - The new code only runs when `parseRefund(msg)` returns null (the rare malformed-refund case), NOT on every refund. For a 10K-message walk where ~0.1% (10 messages) trigger the null path: 10 × ~200ns = 2µs total. Negligible.
  - Even if EVERY refund were malformed (worst case): 10K × ~200ns (one V8 string coerce + one falsy check) = 2ms over a full walk. Still well within tolerance for a one-shot verifier scan.
  - `parseRefund` itself at `hcs20-reader.ts:1562-1573` already does `String(msg.payload.originalDepositTxId ?? '')` and returns null on empty. The dispatcher's coerce is a duplicate read of an already-extracted-and-discarded value. Cost: ~100ns per duplicate.
**Why:** `parseAuditTopic` is invoked from `verify-audit.ts` (offline operator script, not user-facing) and `read-accounting` (CLI). Neither is on the request hot path. Confirmed: no production-latency impact. Minor cleanup opportunity: surface `originalDepositTxId` from `parseRefund` rejection so the dispatcher doesn't re-coerce, but the current cost is < 0.1ms per 10K-walk.

### P11-004 (low) — pendingLedger SADD-before-flush: same Redis round-trip count as before
**Site:** `src/custodial/pendingLedger.ts:287-312` (eager) and `:499-508` (periodic), per commit f3a0431
**Bug:** Phase-8 reorders SADD ↔ flush ↔ LREM. Per-row Redis round-trips:
  - **Before**: SET-NX claim, SISMEMBER applied, updateBalance (in-process), LREM, store.flush() (Redis SET), SADD applied. → 5 Redis ops per applied row (NX, SISMEMBER, LREM, flush-write, SADD).
  - **After**: SET-NX claim (via fencedClaim), SISMEMBER applied, updateBalance, SADD applied, store.flush(), LREM. → Same 5 Redis ops, just reordered.
  - Quantification: 5 × ~1ms RTT (Upstash p50) = ~5ms per applied row, identical pre/post. No throughput change.
**Why:** The reorder is a correctness fix (closes the SADD-after-flush double-debit window), not a performance change. Confirmed no regression. fencedClaim at `src/lib/fencedClaim.ts` adds one DEL on body-throw paths (compare-and-DEL), but happy path is round-trip-equivalent.

### P11-005 (low) — audit-coverage gate iteration is O(27)
**Site:** `src/__tests__/audit-coverage.json` (27 finding entries) consumed by `src/__tests__/audit-coverage.test.ts` and `src/__tests__/audit-coverage-scan.ts`
**Bug:** The Phase-8 manifest grew to 27 entries. The gate iterates linearly to (a) check duplicates, (b) confirm test files exist on disk. Cost: 27 × O(few-µs) per assertion = sub-millisecond per Vitest run.
**Why:** Test-time cost only, not on production hot path. Confirmed negligible. Even at 10× growth (270 entries), the scan stays under 10ms. No action needed.

## Recommended next action (out of scope for this round)
Shard the pending-ledger storage from a single global LIST to per-user keys (`pending:adjustments:{userId}` as either a LIST or HASH). The eager-drain loop already filters to `entry.userId !== userId` after the LRANGE — moving the filter into the key itself collapses the LRANGE to O(user's pending count) instead of O(global pending count). This is the only sub-second-p99 path for `/api/user/status` once cluster-wide pending volume exceeds a few hundred entries.

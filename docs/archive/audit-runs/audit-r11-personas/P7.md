# P7 — Frontend / UX / API Contract Integrity (Round 11)

Scope: did Phase-8 Cluster C (45372d3) preserve wire compatibility on
`/api/user/status`, and what frontend assumptions still ride on the
pre-Phase-8 shape?

## Critical (C)

### P7-C1 — `data.balances` from `/api/user/check-deposits` clobbers pre-subtracted view in dashboard state
`app/dashboard/page.tsx:415-423` and `:579-585` patch `status.balances`
with `data.balances` returned from `/api/user/check-deposits`
(`app/api/user/check-deposits/route.ts:72`). `check-deposits` returns
**raw `user.balances`** (no pending subtraction). The status route now
returns `responseBalances` with pending-debits subtracted. After a
manual or auto-triggered deposit check, the dashboard reverts to the
phantom-funds view that R9-FG-10 / Phase-7-E was shipped to fix —
without re-fetching `/status`, the user sees their refund-pending
amount as available again, and the Withdraw modal's `available` will
let them attempt to withdraw it. Phase-8-C closed the cache mutation
but the merge-back in the dashboard re-introduces the same UX bug
through a different codepath.

### P7-C2 — `/api/user/play` and `/api/user/withdraw` responses also return raw `user.balances`
`app/api/user/play/route.ts:147` and `app/api/user/withdraw/route.ts:161`
return `refreshed?.balances ?? user.balances` directly. Dashboard
patches `setStatus({ ...prev, balances })` at `page.tsx:690` and `:800`.
Same wire-shape mismatch as P7-C1: post-play / post-withdraw the
balance display loses the pending subtraction. This is the load-bearing
path — every successful play flips the dashboard back to the phantom
view. The Withdraw modal then re-opens with `available` = raw, and the
user can trigger a withdraw that the per-user lock will reject at
submit time. Pre-submit UX promise broken.

## High (H)

### P7-H1 — `pendingAdjustments[]` field is wire-only; no TypeScript contract, no UI badge
`app/dashboard/types.ts:30-45` `StatusResponse` interface omits
`pendingAdjustments`. Grep across `app/` shows zero readers. R9-FG-10
spec required surfacing a "queued refund — clears next drain" badge so
the user understands WHY their available dropped. The route emits the
data (route.ts:188); nothing renders it. From a user perspective the
balance just silently shrunk. Risk of support tickets ("why is my
balance lower than my deposit?").

### P7-H2 — `/account` page duplicates `StatusResponse` type and is now drift-prone
`app/account/page.tsx:29-50` re-declares `TokenBalanceEntry` and
`StatusResponse` inline instead of importing from
`app/dashboard/types.ts`. Phase-8-C added fields to the wire shape
(`pendingAdjustments`); both type declarations are now out of sync with
the route. Today /account doesn't render balances so the divergence is
latent, but any future shared component that switches between the two
imports will silently lose the field.

### P7-H3 — Admin refund dashboard discards `code`/`kind`/`retryable` (R10-FG-8 confirmed unfixed in Phase-8)
`app/admin/page.tsx:609-616` reads only `body.error` from the refund
response. `mapErrorToResponse` in `app/api/_lib/errors.ts:38-69`
populates `code: 'REFUND_DUPLICATE'`, `kind: 'in-progress'|'permanent'`,
`retryable: boolean`, and a status-coded HTTP code (409 vs 422). The
operator UI cannot branch — "wait 60s and retry" looks identical to
"call SREM on Redis to unblock". Phase-7-F shipped the structure, P8
did not consume it. R10-FG-8 still open.

## Medium (M)

### P7-M1 — Withdraw modal does NOT independently subtract pending; correct now but fragile
`app/dashboard/WithdrawModal.tsx:71-73` reads `tokenEntry.available`
verbatim. Since `responseBalances` is pre-subtracted, the modal is
correct under the current wire shape. But P7-C1/C2 paths overwrite
that with raw balances mid-session, making the modal sometimes correct
and sometimes wrong depending on which API was the last to update
state. No invariant test pins this.

### P7-M2 — 60s background poll re-overwrites status with `loadStatus` but stale-cache window is 60s
`app/dashboard/page.tsx:486` polls every 60s. Between a deposit-check
patch (which clobbers with raw balances per P7-C1) and the next
quietRefresh, the user is in an inconsistent state for up to 60s. On
mobile (where the visibility-change throttle in :459 = 30s) the window
can extend further if the user doesn't background the tab.

### P7-M3 — `data.balances!` non-null assertions hide the new wire-shape check
`page.tsx:419,570,582` use `data.balances!` non-null assertions when
patching status. If the backend ever returned only `responseBalances`
under a feature flag (e.g. opt-in pending-subtraction), the type guard
would silently coerce. Tighter type narrowing on the response would
catch the mismatch at compile time.

## Low (L)

### P7-L1 — Inline JSDoc comment in `/api/user/status` references R10-FG-2 fix but no public schema doc updated
`route.ts:115-122` documents the fix in code comment only. No update to
`docs/hcs20-v2-schema.md` or any frontend integration doc records the
new `pendingAdjustments[]` field or the `responseBalances`
pre-subtraction semantics. Third-party MCP/A2A clients reading wire
shape have no spec.

### P7-L2 — `tokensToQuery` always pushes 'hbar' but lowercase symbol; collision risk with token-id keys
`route.ts:101` adds literal `'hbar'`. `pendingByToken` uses
`tokenKey` from the ledger (`HBAR` upper or `0.0.X`). If pending HBAR
debits are stored under `'HBAR'` (verify-audit normalizes to uppercase
HBAR) the velocity lookup at `'hbar'` won't find them. Cosmetic in the
HBAR case (only velocity counter is informational), but suggests the
token-key normalization isn't centralized.

### P7-L3 — No mobile-specific responsive tests for new `(displayReserved + pending)` rendering
`page.tsx:1503-1535` renders `Available {amount} {token} ({reserved} in play)`. With pending-subtracted available + reserved + (future
pendingAdjustments badge) the line could overflow on `375px` iPhone
SE width. No CSS responsive test covers the multi-token case; manual
verification only.

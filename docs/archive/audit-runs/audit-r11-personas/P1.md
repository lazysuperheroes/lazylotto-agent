## Findings

### P1-001 (H) — periodic-drain SADD-before-flush has zero behavioral coverage; sibling-site placebo
**Site:** `src/__tests__/r10-fg-1-behavioral.test.ts:1-411` (only exercises eager) vs `src/custodial/pendingLedger.ts:505-518` (periodic path, untested)
**Bug:** The Phase-8D commit message claims both eager (`applyPendingLedgerForUser`) and periodic (`drainPendingLedgerAdjustments`) paths got the SADD-before-flush + no-catch fix. The behavioral test calls only `applyPendingLedgerForUser`. `drainPendingLedgerAdjustments` (the actual cron-driven path that runs without the eager `withUserLock` refresh contract) is not exercised by any test in `r10-fg-1-behavioral.test.ts` — neither the call-order assertion nor the partial-failure replay. Reverting the periodic-path SADD/flush ordering does NOT flip any test, so the sibling site is locked by inspection only. Worse, the periodic body has its OWN `await store.refreshUser(entry.userId)` at line 452 that the eager path doesn't (eager relies on `withUserLock` upstream at `locks.ts:172`); the kill-state recovery contract is structurally different between paths and the test cannot generalize.
**Why:** This is the exact R6-FG-1/R6-FG-2 sibling-site archetype the project documents structurally — the audit cycle keeps finding sibling misses. Locking only the named path means the next round will reopen the periodic side as a fresh "introduction" finding.

### P1-002 (H) — R10-FG-2 "verbatim copy" contract is enforced by promise, not mechanism
**Site:** `src/__tests__/r10-fg-2-behavioral.test.ts:142-202` ("verbatim reproduction") vs `app/api/user/status/route.ts:123-167`
**Bug:** The test's `applyPendingAdjustmentsLikeRoute` is described as a "verbatim reproduction" of the route block, with the regression-detection contract that "changes to the route's logic require a paired update to the test, otherwise the two diverge silently." This is exactly an honor-system contract — there is no checksum, no string-extraction gate, no lint rule comparing the two. The test never imports the route handler. The route can be regressed (e.g., re-add `user.balances = adjustedBalances` at line 166) and the test continues to pass against its frozen copy. The commit message itself acknowledges this trade-off but ships no enforcement. Already drifted: the test fixture wraps in `try { ... } catch { /* informational only — leave pendingAdjustments empty */ }` (test:198) while the route wraps in `try { ... } catch { /* pending-ledger lookup is informational; if it fails just return the raw store balances and skip the badge. */ }` (route:168) — different comments, same logic, but the divergence in a "verbatim" file is itself the proof-of-concept that the contract isn't enforced.
**Why:** The fix's regression-lock claim is false advertising. Reverting the actual route flips zero tests. This is the same test-claims-vs-behavior gap that R10-FG-4 was supposed to close.

### P1-003 (H) — R10-FG-4 "placebo gate" closure is itself the placebo it claims to close
**Site:** `src/__tests__/audit-coverage.test.ts:178-193` (new gate) vs `src/__tests__/audit-coverage.json:341-617` (R9-FG-1, 2, 3, 4, 6, 8, 11, 12, 13)
**Bug:** The R10-FG-4 finding said 9 of 12 R9-FG entries shipped with `coverageStrategy:'individual'` AND `tests:[]`, vacuously passing the cross-check. Phase-8 Cluster A's "closure" adds a new gate (`empty.length === 0` for `coverageStrategy === 'individual'`). But the *actual* method of closure was to **downgrade those exact 9 entries to `coverageStrategy: 'documentation-only'`** with a uniform sweep note (audit-coverage.json:388, 416, 436, 454, 477, 528, 550, 598, 617 — all carry the verbatim string `"Phase-8 R10-FG-4 sweep: downgraded individual→documentation-only; per-finding behavioral test deferred"`). The new gate at line 128-129 explicitly skips `documentation-only` AND `structural-gate` entries (`if (f.coverageStrategy === 'documentation-only') continue;`). Net effect: 9 critical/high R9 entries that previously passed via empty-array vacuity now pass via documentation-only waiver — same archetype, renamed label. R9-FG-6 (the very SADD race that caused R10-FG-1) is in the downgrade list. R9-FG-1, R9-FG-2, R9-FG-3, R9-FG-13 (4 critical/high) downgraded. Adding any new individual-strategy bug with `coverageStrategy: 'documentation-only'` and a sweep-note rationale now bypasses the gate by design.
**Why:** The gate looks tightened but the escape-hatch policy was widened to compensate. A reviewer trusting `npm test` green to mean "all individual-strategy entries have real tests" gets an honest answer ONLY for entries someone bothered to label individual. The placebo-by-elision archetype recurs.

### P1-004 (M) — R10-FG-1 fix's own documented "silent loss" branch (flush throws after SADD) has no test
**Site:** `src/custodial/pendingLedger.ts:300-307` (comment) vs `src/__tests__/r10-fg-1-behavioral.test.ts:42-52, 305-409` (only `saddBroken` exercised)
**Bug:** The fix's inline contract documents three failure modes: (a) SADD throws → claim released, retry clean, (b) flush throws → applied-set is a poison-pill, debit silently lost (acceptable per audit), (c) LREM throws → idempotent under SISMEMBER. The mock state has `saddBroken` and `lremBroken` flags, but no `flushBroken` flag. Test (a) is exercised; test (c) is implicit; test (b) — the documented "silent loss" trade — is not. Future regressions that re-introduce a flush-failure path producing double-debit (e.g. a developer "fixing" the silent loss by reverting the SADD ordering) would not be caught — the test's hypothesis is "flush-then-SADD double-debits", but only the SADD-throw arm is asserted. The audit's "silent loss vs double-debit" trade is invisible to CI.
**Why:** The comment-vs-code mismatch archetype the round-10 audit named for pendingLedger now lives in the comment-vs-test mismatch shape: the body docs three branches, the test asserts one.

### P1-005 (M) — `kind:'busy'` continue branch sets no progress timer; relies on orphan reconciler 7d TTL with no test
**Site:** `src/custodial/pendingLedger.ts:339-356` (eager) and `:536-545` (periodic), `src/lib/orphanReconciler.ts:97` (`pendingLedgerClaim: 7 * 24 * 60 * 60`)
**Bug:** Phase-8's R8-FG-7 fix changed both busy branches from "best-effort LREM" to "leave the row, continue." The inline rationale claims "next drain pass re-acquires." For a Lambda-kill-before-fenced-body-runs scenario (kill window between `redis.set NX` and the body's first `await`), `fencedClaim`'s catch does NOT fire (no throw to catch — process just dies). The fence claim sits stuck for the full `ttlSec: 7 * 24 * 60 * 60` (line 322 / line 520). Recovery relies entirely on the orphan reconciler at `orphanReconciler.ts:97`, but per the round-10 audit's R10-FG-6 cluster (8-agent confirm) that subsystem has no debounce, no per-namespace ratio, swallows failures via `console.error`, and the staleThresholdRatio = 0.75 × 7d = 5.25 days before the user's pending refund is even surfaceable as orphaned. There is no behavioral test in `r10-fg-1-behavioral.test.ts` exercising the busy-branch + reconciler interaction; `state.kv` in the mock never simulates a stale-fence scenario. Net: under Lambda-kill-mid-acquire, the user's pending refund row is queued, the eager path returns busy on every dashboard refresh, the user sees a stuck `pendingAdjustments` entry for ~5+ days before alarm potential. Severity downgraded to M because the row is preserved (not lost) and the orphan reconciler does target this namespace — the gap is observability + recovery latency, not data loss.
**Why:** The Phase-8 fix correctly preserves the queue row but its proof-of-recovery test is absent. The 7d TTL window the round-6 R6-FG-12 audit closed at one site is structurally back here under a Lambda-kill-before-body scenario the test suite does not exercise. Combined with the R10-FG-6 cluster's known reconciler observability gaps, this is a 5+ day silent stale-claim window with no CI lock.

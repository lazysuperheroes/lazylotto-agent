## Findings

### P4-001 (C) — Comment claims a non-conservation alert surfaces silent loss; no such alert exists
**Site:** `src/custodial/pendingLedger.ts:305-307` and (mirror) `:505-509`. Cross-checked against `src/scripts/verify-audit.ts` (full-file grep).
**Bug:** The new comment says: "The debit is silently lost — acceptable per the audit's 'silent loss vs. double-debit' trade. The reconcile cron's debit-vs-refund-anchor cross-check surfaces silent loss as a non-conservation alert." Grep across `verify-audit.ts`, `verify-audit-crosscheck.ts`, and `app/api/cron/reconcile/route.ts` finds NO consumer that compares `pendingLedgerAppliedSet` membership against the union of (HCS-20 refund anchors) ∪ (delivered debit operations). There is no `non_conservation`/`debit_lost`/`pending_ledger_orphan` alert anywhere. The only thing close is the verify-audit `user_balance_negative` critical (which fires on the OPPOSITE direction). When flush throws, the applied-set entry remains as a poison pill, the LIST row is LREM'd on the next pass via the `alreadyApplied` short-circuit, the user's balance was NEVER debited, the deposit credit lives on, and no operator page ever fires.
**Why:** This is the central justification for the trade-off the Phase-8 commit ships. "Silent loss is acceptable because reconcile catches it" is the only thing distinguishing this design from "we silently keep the user's refunded money and move on." Without the cross-check, this is unaccounted-for permanent ledger drift that is not surfaced to operators. Severity = critical because every Redis flush failure during a refund drain produces a phantom credit equal to the full refund amount, undetected.

### P4-002 (H) — `pendingLedgerAppliedSet` has no TTL and grows unboundedly; sole use is `SISMEMBER` on hot drain path
**Site:** `src/auth/redis.ts:60` (declares set with explicit "No TTL" comment); `src/custodial/pendingLedger.ts:241,311-314,440-443,510-513`.
**Bug:** Every refund SADDs into ONE global set keyed `lla:<net>:pending-ledger-applied`. There is no sharding, no expiry, and no GC. After Phase-8, every `withUserLock` call (every play, every withdraw, every status poll, every register, every refund) calls `applyPendingLedgerForUser`, which LRANGE'es the global pending list and for every matching row calls `redis.sismember(pendingLedgerAppliedSet, "<userId>:<sourceTx>")`. SISMEMBER on a Redis SET is O(1), so latency is fine — but per-key memory grows without bound. At a steady-state of ~5 refunds/user/day × 10K users × 365 days × ~50-byte members ≈ 90MB per year, retained forever. Upstash bills storage. More importantly: there is no recovery path if the set grows past the request budget on a Redis dump/restore.
**Why:** The author explicitly chose "no TTL" because once a row is applied, it must stay applied forever (otherwise the double-debit window re-opens after expiry — which is exactly what R10-FG-1 closed). So a TTL fix is unsafe. The right fix is a monthly-shard scheme (`pendingLedgerAppliedSet:YYYYMM`) with a 90-day rolling SISMEMBER fan-out across the last 3 shards, or an LREM-based GC on `lpush` time + a LIST-of-applied per-user. Both require schema changes that Phase-8 did not ship. Same archetype as R10's "pendingLedgerAppliedSet unbounded growth" (4 confirms in round-10), still open.

### P4-003 (H) — withUserLock swallows applyPendingLedgerForUser throw, then `fn()` runs against in-memory mutation that was reverted
**Site:** `src/lib/locks.ts:177-189` (the catch around `applyPendingLedgerForUser`) interacting with `src/custodial/pendingLedger.ts:228-337`.
**Bug:** Phase-8 specifically changed the eager-path to NOT swallow SADD/flush throws, so they propagate out of `applyPendingLedgerForUser` to `withUserLock`. But locks.ts:182-189 catches that throw with `console.warn` and CONTINUES into `await fn()`. The behavioral test (`r10-fg-1-behavioral.test.ts:370-385`) only validates the RE-ENTRY case, where a second `withUserLock` invocation runs `refreshUser` and pulls clean state. Within the SAME invocation, the sequence is: (1) refreshUser pulls persisted=100, (2) drain runs, calls `store.updateBalance` setting in-memory available to 90, (3) SADD throws, (4) fencedClaim catch releases, (5) the throw propagates to locks.ts:182, (6) caught, warn logged, (7) `await fn()` runs against the in-memory cache that still shows 90. The user is now operating on a debited cache for the rest of the lock body, even though Redis says 100. If `fn()` triggers a flush internally (e.g. play settlement, withdraw debit), the 90 lands in Redis with no SADD entry — which then re-triggers the very R10-FG-1 double-debit on the next drain. The "rollback via refreshUser" is only valid if there's no further work in the same lock body, which is the OPPOSITE of withUserLock's purpose.
**Why:** Locks.ts:181 explicitly documents "Worst case the cron drain catches this entry on the next reconcile" — but that's only true if the in-memory mutation is also reverted before `fn()` runs. The fix would be to call `store.refreshUser(userId)` again inside the catch block, or to escalate the throw. Neither happens. This re-introduces the R10-FG-1 archetype through a different door whenever the eager drain is followed by any in-band balance operation.

### P4-004 (M) — `refund.ts:1442` and `:1987` retain pre-Phase-8 `await store.flush(); catch { /* */ }` with no SADD-style poison-pill anchor
**Site:** `src/hedera/refund.ts:1441-1445` and `src/hedera/refund.ts:1986-1990`.
**Bug:** Phase-8 audited `pendingLedger.ts` for the `flush + .catch(() => 0)` archetype and removed the swallow. But `refund.ts` retains the same archetype at two sites: `try { await store.flush(); } catch { /* */ }` followed immediately by `store.upsertDeadLetter`/resolve writes that depend on the flush having landed. If flush throws, the catch silently continues, the resolve marker is then write-through-cached AND fired into the same Redis that just rejected the prior write. Either (a) the second write also fails — in which case both are in cache only, and the response returns success — or (b) the second succeeds in isolation, and Redis state is now: resolve marker present, but the prior verifier mutations (debit, audit anchor, rake reversal) are lost. There's no SADD poison-pill applied-set guarding this — the resolve marker itself is the only trace, and it is by definition the LAST write, so it cannot detect dropped predecessors.
**Why:** This is the same R10-FG-1 archetype family in a different module. R10-FG-15's audit fix was scoped narrowly to `pendingLedger.ts` flush swallow; the sibling pattern in the much hotter refund verifier path is untouched. The reviewer-style claim "Phase-8 closed flush-failure swallow" is true for one module, false for the codebase. P3's gate (claim-archetype-gate) is regex-based on `nx: true` and does not catch `flush + .catch`.

### P4-005 (M) — Eager-path catch at pendingLedger.ts:329-336 dismisses real Phase-8 failure modes as "impossible in practice"
**Site:** `src/custodial/pendingLedger.ts:324-337` (eager catch); mirror at `:522-534`.
**Bug:** The catch comment says: "fencedClaim only rethrows on PreserveClaimError. The body doesn't submit on-chain actions so this branch is impossible in practice, but if it ever fires we propagate so callers see the failure instead of silently corrupting the queue." Post-Phase-8 the body now contains TWO awaits that can throw and are NOT preserve-claim: `await redis.sadd(...)` (line 311) and `await store.flush()` (line 315). fencedClaim's catch at fencedClaim.ts:181 calls `releaseFence` (a `redis.eval` followed by best-effort `redis.del`) and then RETHROWS the original error. So the eager body IS expected to hit this catch on Redis blips — that's the entire reason Phase-8 removed `.catch(() => 0)`. The catch then `failed++` and `continue`s the for-loop, leaving the in-memory user object with an applied debit (from `store.updateBalance` on line 256-261) and skipping over the row. The next drain in the same Lambda will re-run `applyPendingLedgerForUser`, which will LRANGE the row again, see SISMEMBER=0 (Redis SADD never landed), and re-debit on top of the in-memory debit that's still sitting there. Locks.ts has not yet released — the same `withUserLock` body is still running. P4-003 above and this finding are the same archetype seen from two angles.
**Why:** The comment is comment-vs-code mismatch in the immediate vicinity of the new code. Pre-Phase-8 the body had no awaits other than fencedClaim's own primitives that ran inside the body (LREM was best-effort). Post-Phase-8 the body has SADD + flush bare. The catch should be hardened: either escalate (throw out of `applyPendingLedgerForUser`) so `withUserLock` sees the failure and the next acquirer's `refreshUser` rolls back the in-memory state, or call `store.refreshUser(entry.userId)` inside the catch to revert the dirty balance.

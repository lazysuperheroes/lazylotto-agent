## Findings

### P2-001 (severity: H) — `SignatureValidationError` migration still incomplete (R10-FG-14 unfixed in Phase-8)
**Site:** `src/auth/verify.ts:87, 94, 154`
**Bug:** Phase-8 did not touch `src/auth/verify.ts`. Three security-critical throws are still plain `Error`:
- L87 `throw new Error('Challenge expired or already used');`
- L94 `throw new Error('Challenge was issued for a different account');`
- L154 `throw new Error('Signature verification failed');`
Only the SignatureMap-decode block (L104, L113, L121) uses the typed sentinel.
**Attack:** Any caller that wants to react to "real signature failure vs decode failure" must fall back to `err.message.includes('signature')` substring matching — exactly the R8-FG-25 archetype the sentinel was created to retire. A future copy-edit of message strings (translation, log scrubbing, error-aggregator masking PII) silently flips downstream logic. Plus, the most security-sensitive throw — "Signature verification failed" at L154 — gets bucketed into the same `Error` class as a generic decode error, so logging/alerting cannot prioritize cryptographic failures.
**Why it matters:** R9-FG-5 closure was advertised as complete; it isn't. The whole point of the typed sentinel was to make signature-validation an `instanceof` check instead of a substring check. Half-migrated code is worse than unmigrated code because callers think they're using the discriminator.

### P2-002 (severity: H) — Velocity-counter inflation 24h-DoS (R10-FG-12 unfixed in Phase-8)
**Site:** `src/custodial/MultiUserAgent.ts:2558-2569`
**Bug:** `redis.incrby(key, amount)` is committed unconditionally; the comment at L2548-2557 explicitly says "we don't roll back" on the over-cap branch ("velocity-cap counters are intentionally lossy on the over-cap edge").
**Attack:** Compromised session token (or a user re-using a token after lock revocation race) issues `withdraw(1500)` 10 times in succession. Each call drives `incrby(key, 1500)` → counter to 15000 against a 1000 cap. Every legitimate withdraw for the next 24h returns `proposed > cap` → 503. Combined with R10-FG-12: there is no rollback even when the withdrawal *itself* fails for an unrelated reason (e.g. ledger debit fails, on-chain submit fails). Single API call can permanently lock a victim's daily allowance.
**Why it matters:** The comment frames this as "the user can't actually spend it" — true, but the attacker's goal here isn't theft, it's **denial of service against a specific victim's withdraw modal**, which is the most user-trust-critical surface in the app. Trivial fix: `INCRBY` then `DECRBY(amount)` on the over-cap branch (or any throw before SDK submit).

### P2-003 (severity: H) — `parseRefund` null-drop is only partially categorized (R10-FG-3 fix incomplete)
**Site:** `src/custodial/hcs20-reader.ts:643-652` (dispatcher); `src/custodial/hcs20-reader.ts:1558-1574` (parser)
**Bug:** Phase-8 added `stats.refundsDroppedEmptyOriginal` for the `!originalDepositTxId` null-return at parser L1573. But `parseRefund` *also* returns null at L1574 when `!from || !to || !Number.isFinite(amt) || !refundTxId`. The dispatcher only categorizes the empty-`originalDepositTxId` branch; the four other null-return reasons fall through into the catch-all `skippedMessages++`.
**Attack:** A legacy or attacker-injected refund anchor with valid `originalDepositTxId` but missing `refundTxId` or non-numeric `amt` still drops silently — verify-audit's reconstruction OVER-CREDITS the user by the refund amount, with no recoverable signal. Same R10-FG-3 archetype, different sub-branch.
**Why it matters:** Phase-8 advertised closure of "parseRefund silent null over-credits user" — only the most obvious branch is closed. Comment-vs-code mismatch in pristine form: the docstring at the dispatcher reads "categorize the null-drop" (singular) but only one of five null-return causes is categorized. The dissection doc warned about exactly this archetype recurring.

### P2-004 (severity: H) — Pending-ledger applied-set has no TTL → unbounded Redis growth → DoS via parser CPU
**Site:** `src/auth/redis.ts:60` (declares `pendingLedgerAppliedSet` with explicit "no TTL"); `src/custodial/pendingLedger.ts:311-314, 510-513` (SADD calls)
**Bug:** Phase-8 fix for R10-FG-1 is correct on the SADD-before-flush ordering, but the applied set is `SADD`-only and has no TTL by design. Plus `listPendingLedgerAdjustments()` (`pendingLedger.ts:100-120`) is `LRANGE 0 -1` over the global queue, called once per `/api/user/status` poll for every user.
**Attack:** Two compounding vectors:
  1. *Storage-cost amplifier.* An attacker who can trigger refund-uncertain DLs (admin-controlled, but admin compromise scenario) causes monotonic SADD growth — 100k+ entries over months. Upstash bills storage; entries are full `userId:sourceTx` strings, ~80 bytes × N.
  2. *CPU-DoS via dashboard.* The status route's `listPendingLedgerAdjustments()` LRANGE pulls the entire (unbounded) global queue, JSON-parses each row, and JS-filters by userId on every dashboard mount/visibility-refresh. R10-FG-11 already documents this as performance-critical. Combined with the applied-set growth, the warm-Lambda CPU budget gets eaten by serialization of refund history a victim never had.
**Why it matters:** R10 medium notes already flagged the unbounded growth (4 confirms). Phase-8 didn't add TTL or sharding. Coupled with the LRANGE on hot path, two warm Lambdas amplify the issue under load.

### P2-005 (severity: H) — Pending-ledger applied-set poisoning silently nulls victim refund credits
**Site:** `src/custodial/pendingLedger.ts:241-246, 440-448` (SISMEMBER short-circuit branches); applied-set key format `${userId}:${sourceTx}`
**Bug:** Phase-8 made SADD-before-flush atomic. But the SISMEMBER pre-check is the **first** thing the body does — if a member exists for `${userId}:${sourceTx}`, the body `lrem`s the queue row and returns `already-applied` *without* checking whether the in-store balance was actually adjusted. The applied set is the sole source of truth for "has been applied"; any path that can SADD an entry for a victim's `(userId, sourceTx)` pair without the corresponding store mutation silently consumes the next refund row for that pair.
**Attack:** The attack surface depends on whether SADD can be triggered out-of-band. Two realistic vectors:
  1. *Lambda-kill mid-flush propagation.* Phase-8's own commit message acknowledges "flush throw → applied-set entry stays as a poison-pill; next drain takes the already-applied branch ... debit is silently lost — acceptable per the audit's silent loss vs double-debit trade." This is a deliberate design choice but still a viable DoS: an attacker who can induce flush failures (Redis hiccup, store exhaustion) causes the victim's refund debit to permanently disappear from the in-store ledger while the topic shows the refund. Verify-audit's reconstruction will read the topic and credit the user back the refund — *this leaves the user's effective balance accidentally HIGH*, not low. Silent loss is asymmetric: lost-debit on the operator side becomes phantom-funds for the user.
  2. *Operator-side compromise.* Anyone with `redis SADD` access (admin debugging, recovery scripts) can pre-poison entries. No fence prevents this since the anchor is keyed only on `(userId, sourceTx)` with no signature.
**Why it matters:** The Phase-8 commit message frames "silent loss" as a closed trade-off, but conflates "operator-side debit lost" with "user gains phantom funds via verify-audit reconstruction." Those are different security postures. The reconciliation cron's "non-conservation alert" is the only safety net; the alert is documented but the wiring (R10-FG-9 aggregate ledgerBalance) is also documented as broken.

### P2-006 (severity: M) — `responseBalances` info leak to other authenticated users on warm Lambda race
**Site:** `app/api/user/status/route.ts:130-167`
**Bug:** Phase-8 fixed the cache-mutation by introducing `let responseBalances = user.balances` then reassigning the local on adjusted-balance branch. But `user` is fetched via `store.getUserByAccountId(accountId)` (L56) which returns a **live reference** to the store cache (`RedisStore.refreshUser` on L377 does `this.users.set(account.userId, account)`). On the unadjusted branch (no pending), `responseBalances` is *still the live store reference* and gets serialized into the JSON response. If a concurrent request for the same userId mutates `user.balances` *between* the assignment at L130 and the `NextResponse.json` at L173 (e.g. a play session writing to the in-memory store before flush), the response body sees the partially-mutated object.
**Attack:** Two concurrent /status calls + one /play call on the same warm Lambda. Play call mid-flight mutates `user.balances.tokens.X.available` between status request 1's L130 and L173, status returns balances reflecting an in-flight play that hasn't been committed. Inverse of R10-FG-2: phantom DEFICIT in the response, but transient and only on warm-Lambda concurrent requests.
**Why it matters:** Phase-8 closed the *persistent* mutation but not the *transient* live-reference exposure. The fix at L130 should be `let responseBalances = { ...user.balances, tokens: { ...user.balances.tokens } }` unconditionally to detach from the live cache. Currently the no-pending branch still aliases.

### P2-007 (severity: M) — `/api/user/status` velocity probe leaks token-set existence cross-tenant
**Site:** `app/api/user/status/route.ts:100-102` and `src/custodial/velocity.ts:67-72`
**Bug:** `tokensToQuery = Object.keys(user.balances.tokens)` is built from the user's own balance set. Each token spawns a Redis GET against `KEY_PREFIX.velocity:<token>:<userId>`. The velocity response includes `cap` for every token even if the user has zero usage. An attacker with a session token who can register a user can register multiple users and query velocity caps for arbitrary token IDs by crafting balance entries — surfaces operator's `WITHDRAWAL_DAILY_CAP_<TOKEN>` env var values across the deployment.
**Attack:** Mostly informational — operator caps aren't sensitive. But it's an enumeration primitive: an attacker can probe whether the operator has configured a velocity cap for a particular token without onboarding the token. The cap is per-environment and would otherwise require Vercel env access to read.
**Why it matters:** Low-severity info leak; classified medium because it's reachable without admin auth and discloses operator configuration.

### P2-008 (severity: M) — `.message.startsWith` archetype family unguarded (R10-FG-13 unfixed)
**Site:** `src/hedera/refund.ts:339`, `src/custodial/AccountingService.ts:864`
**Bug:** R10-FG-13 documented two live `.message.startsWith(...)` sites; the sibling-archetype gate (`src/__tests__/sibling-archetype-gate.ts`) regex still only catches `.message.includes`. Both call sites contain literal-string matching against an upstream error message; a copy-edit of those messages silently flips control flow.
**Attack:** Standard R8-FG-25 family — change "Cannot refund deposit" upstream and the catch in `refund.ts` no longer fires, surfacing internal state to the operator surface or letting a refund proceed where it shouldn't. Same archetype Phase-6 closed for `.includes`.
**Why it matters:** Phase-8 didn't touch the gate; the archetype family is open. Trivial extension: regex `(?:includes|startsWith|endsWith|match|search|indexOf)`.

### P2-009 (severity: L) — Boot-warning for `HCS20_SOFT_VALIDATE` only fires on Vercel
**Site:** `src/custodial/hcs20-reader.ts:maybeFireBootWarning`
**Bug:** `process.env.VERCEL === '1'` gates the warning — only fires on Vercel deployments. A self-hosted production deploy (or any non-Vercel runner) never sees the schema-drift-detection-disabled warning. Operationally the schema-drift detector silently ships dead.
**Attack:** Not exploitable; hardening gap. A self-hosted deploy ships without realizing they're missing the soft-validate signal.
**Why it matters:** L because the production-required asserts (`assertProductionRedis`) catch missing critical env, but `HCS20_SOFT_VALIDATE` is observability-only.

### P2-010 (severity: L) — Pending-ledger queue contains victim PII (userId + tokenKey + amount + sourceTx) with no TTL
**Site:** `src/custodial/pendingLedger.ts:81` (rpush) and `src/auth/redis.ts:41` (LIST_KEY definition — no TTL anywhere)
**Bug:** Failed/deferred refund rows live in the queue indefinitely. The applied-set anchor prevents double-debit, but the queue row itself is only LREM'd on success or user-not-found. A row that hits the SADD-before-flush poison-pill branch *stays in the queue* forever (the next drain takes the already-applied path and LREMs there). But if SADD also fails (transient Redis), the row stays *and* the applied-set is empty → next drain reprocesses cleanly. In either case, the queue accumulates user-financial-history rows that any anyone with Redis read access can `LRANGE`.
**Attack:** Operational risk only; needs Redis read access. But combined with `listPendingLedgerAdjustments()` returning the global queue to `/api/user/status` (filtered in JS, not in Redis), a JS-filter regression would expose other users' pending refund history. Defense-in-depth gap.
**Why it matters:** L because the route does filter; the architectural shape (global queue, JS filter, no Redis-side userId index) is fragile. R10-FG-11 already flagged the perf cost; the privacy posture is the silent corollary.

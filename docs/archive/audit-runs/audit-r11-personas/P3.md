### P3-002 (severity: C) — pendingLedger SADD-before-flush comment contradicts production caller flow
**Site:** `src/custodial/pendingLedger.ts:281-308` (the new comment); `src/lib/locks.ts:172-191` (the actual caller).
**Comment claim:** verbatim at `pendingLedger.ts:296-298`: "updateBalance's in-memory mutation is reverted when the caller's `withUserLock` runs `store.refreshUser` at lock-acquire time (locks.ts:172)."
**Code reality:** `withUserLock` runs `store.refreshUser` at line 172 *before* `applyPendingLedgerForUser` at line 181. If SADD throws inside the body, `fencedClaim` releases the fence and rethrows; pendingLedger's outer catch (line 324) swallows with `failed++; continue`. No refreshUser is ever called between the failed SADD and `await fn()` at locks.ts:191. The dirty in-memory `live` user (debit applied but un-flushed) is what `fn()` (the user's play/withdraw) reads. Then locks.ts:197 flushes it. The Phase-8 comment cites a refreshUser that the caller does not run at the claimed time.
**Why it matters:** Same comment-vs-code archetype Phase-8 was created to prevent, recurring inside the Phase-8 fix itself. The R10-FG-1 behavioral test passes because the test's mock store explicitly calls `refreshUser` between drains; production's `withUserLock` doesn't. Test passes, bug shape persists in a different form (single-Lambda dirty-cache double-debit instead of cross-Lambda race).

### P3-003 (severity: C) — R10-FG-2 test is a verbatim copy; route is never imported
**Site:** `src/__tests__/r10-fg-2-behavioral.test.ts:142-202` (verbatim block); `app/api/user/status/route.ts:107-167` (the actual route).
**Comment claim:** test header at lines 22-29: "this test exercises the EXACT mutation block from the route (lines 114-159, verbatim) … A fix to the route MUST be paired with a fix to this test (or the inline copy removed) so the two stay in sync."
**Code reality:** the test imports nothing from `app/api/user/status/route.ts`; it imports `listPendingLedgerAdjustments` and re-implements the route's logic in `applyPendingAdjustmentsLikeRoute()`. A future commit that reverts only the route (re-introduces `user.balances = adjustedBalances`) would leave this test green. The "MUST be paired" contract is enforced by nothing — no gate scans both files for divergence; no import wires the test to the live code path.
**Why it matters:** The test buys regression detection against a copy of the bug, not against the bug. If the route gets refactored (the next R5-100-style sweep), the verbatim copy drifts silently — Phase-8's own dissection documented this as a "regression-detection trade-off" but did not enforce it. Same Goodhart archetype the manifest gate (R10-FG-4) was created to defeat.

### P3-009 (severity: M) — Eager-path SADD-throw silently increments `failed++` and continues to next entry
**Site:** `src/custodial/pendingLedger.ts:329-336`.
**Comment claim:** lines 325-328: "fencedClaim only rethrows on PreserveClaimError. The body doesn't submit on-chain actions so this branch is impossible in practice".
**Code reality:** The branch is not impossible — Phase-8 added `await redis.sadd(...)` and `await store.flush()` inside the body without `.catch`. The catch then `continue`s the for-loop to the next entry while the user's mid-mutation row is left in place AND the live in-memory user object remains debited.
**Why it matters:** Comment-vs-code mismatch in the immediate vicinity of the new code. The "impossible in practice" claim is false post-Phase-8; it was true pre-Phase-8 (no awaits other than fencedClaim's own primitives ran inside the body).

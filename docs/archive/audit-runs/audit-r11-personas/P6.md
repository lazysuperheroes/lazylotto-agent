## HIGH

### `[ ]` P6-R11-H1 — `refundsDroppedEmptyOriginal` is unobservable in production
**Files:** `src/custodial/hcs20-reader.ts:307`, `src/custodial/hcs20-reader.ts:653`
(increment site), `src/scripts/verify-audit.ts:1291-1296` (consumes
`schemaValidationFailures` but NOT `refundsDroppedEmptyOriginal`),
`app/api/cron/reconcile/route.ts:251` (response payload — does not surface it).
The Phase-8B counter exists and increments correctly, but no consumer looks at
it: verify-audit prints `skippedMessages` (line 382) and walks
`schemaValidationFailures` (line 1296), neither covers the new field. The cron
route returns `result + orphanCount` but not reader stats. The user-facing
`/api/user/audit` page is the only surface that could see it, and operators
do not poll user-audit pages. The intended R10-FG-3 "recoverable signal"
ships emitting into `/dev/null` from an operator perspective — the same
wire-only failure mode R9-FG-3 / R9-FG-4 hit in Phase-7.
**Fix:** Surface `refundsDroppedEmptyOriginal` in the cron response payload
alongside `orphanCount`, AND in `verify-audit.ts` summary output, AND fire
`RECONCILE_FAILURE_WEBHOOK_URL` when the value is non-zero.

### `[ ]` P6-R11-H2 — Incident playbook has no entry for orphan-reconciler page or status-code 409/422 (R10-FG-6, R10-FG-7)
**File:** `docs/incident-playbook.md` (no orphan-reconciler symptom entry; no
HTTP-code-map entry). The cron route now fires
`RECONCILE_FAILURE_WEBHOOK_URL` when `orphans.count >=
ORPHAN_RECONCILER_PAGE_THRESHOLD` (`app/api/cron/reconcile/route.ts:230-246`).
On testnet first deploy, the refunded-namespace 30d TTL guarantees a baseline
that exceeds the default threshold of 5 — operators paged with no runbook
section. R10-FG-7 (status-code 500→409/422 monitoring blind spot) is also
unaddressed: `docs/uptime-monitoring.md` Layer 2 still says "page on `solvent:
false`" with no mention of admin refund returning 409/422, and external
monitors configured per the existing runbook will silently miss every
duplicate-refund signal.
**Fix:** Add Symptom 26 (`orphan reconciler page`) and Symptom 27 (`HTTP code
map for /api/admin/*`) to incident-playbook; add a "page on 4xx ≥ 422 from
/api/admin/*" line to `docs/uptime-monitoring.md`.

### `[ ]` P6-R11-H3 — `audit:revert-drill` script ships uninvoked from CI
**Files:** `package.json:37` (declares `audit:revert-drill`),
`src/scripts/run-revert-drill.ts`, `src/__tests__/revert-drills/*.patch`.
The revert-drill harness was authored as a test-the-tests gate but
`.github/workflows/ci.yml` only invokes `npm test`, `schema:docs:check`, and
`audit:coverage:check`. A revert that flips one of the patched lines passes
CI silently because no workflow step runs the drill. This is the same
wire-only-gate archetype the R10 dissection identified — gate code lands,
production CI does not invoke it.
**Fix:** Either (a) add a `npm run audit:revert-drill` step to ci.yml after
`audit:coverage:check`, or (b) explicitly delete the script and patch
fixtures and document the decision in the dissection doc.

### `[ ]` P6-R11-M2 — `HCS20_SOFT_VALIDATE` documented as Phase-7-set-via-env-var, but Phase-7 already hard-sets it at module load (R10-FG-5 unmitigated)
**Files:** `app/api/cron/reconcile/route.ts:55`, `src/scripts/verify-audit.ts:52`,
`docs/mainnet-deploy-checklist.md:125`. The cron route does
`process.env.HCS20_SOFT_VALIDATE = '1'` at module load. In a warm Vercel
Lambda that handled a cron tick and now serves `/api/user/audit`, that env
mutation persists across the module graph (R10-FG-5). The Phase-8 dissection
acknowledges this in the round-10 doc but the fix was not shipped in Phase 8;
the deploy checklist tells operators to also set the env var, which doubles
the surface but does not address the pollution. Operators reading the
checklist may assume they're done.
**Fix:** Either ship the per-walk snapshot fix (P10-010) in a Phase-9, OR
update the checklist to note "this is a known-issue carry-forward — see
R10-FG-5 in `docs/audit-2026-05-09-round10.md`".

### `[ ]` P6-R11-M3 — `audit-coverage.test.ts` runs twice per CI execution
**Files:** `package.json:36` (`audit:coverage:check` script),
`package.json:41` (`test` script glob `src/__tests__/*.test.ts`),
`.github/workflows/ci.yml:38` (runs `npm test`) and `:49` (runs
`audit:coverage:check`). The test glob already matches
`src/__tests__/audit-coverage.test.ts` so the gate runs as part of `npm
test`; the explicit `audit:coverage:check` step at workflow line 49 is a
redundant re-run. Cost: trivial. Risk: a future refactor drops the redundant
explicit invocation, then someone separately changes the `npm test` glob and
the gate silently exits CI. Better to make the dependency explicit.
**Fix:** Either remove the redundant step OR make `npm test` exclude the
gate file and rely on the explicit step. The current setup obscures which
invocation is load-bearing.

### `[ ]` P6-R11-M4 — Disaster-recovery doc not updated for refund-drop archetype
**File:** `docs/disaster-recovery.md`. The Phase-8B closure means a
post-Redis-loss reconstruction from the topic alone is now sensitive to
`refundsDroppedEmptyOriginal` — if the counter is non-zero, the
reconstruction over-credits the affected user (the exact failure mode
R10-FG-3 warns about). DR runbook must say "before trusting the reconstruction,
verify `result.stats.refundsDroppedEmptyOriginal === 0`; non-zero entries
need manual triage from the topic." Without this, an operator following
disaster-recovery.md verbatim post-incident reconstructs an over-credited
ledger.

### `[ ]` P6-R11-M5 — Downgraded "documentation-only" R9-FG entries lose runbook anchoring
**File:** `docs/audit-2026-05-09-round9-fix-tracker.md`, Phase-8A commit
`037f5ba` downgraded R9-FG-1, 2, 3, 4, 6, 8, 11, 12, 13 from

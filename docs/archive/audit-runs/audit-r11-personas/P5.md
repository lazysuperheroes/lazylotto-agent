**Focus:** Phase-8 Cluster B `refundsDroppedEmptyOriginal` consumer audit; conservation invariant 3

## Verdict at a glance

Phase-8 Cluster B is the Phase-6 **wire-only-closure** archetype recurring at the dispatcher.
The counter is declared, incremented, and tested for existence. **No reducer reads it.** The
behavioral test (`r10-fg-3-behavioral.test.ts:91`) was authored to assert the *signal*, not the
*invariant* — it passes against any implementation that increments the counter, including the
current one which still over-credits user balance because verify-audit's reducers don't subtract
the dropped refund amount from anywhere.

R10-FG-9 (aggregate ledgerBalance formula) and R10-FG-16 (heldByToken not decremented on
prize_recovery) are **still OPEN** — Phase-8 did not touch verify-audit.ts.

## Findings (10)

### `[ ]` R11-P5-001 (C) — `stats.refundsDroppedEmptyOriginal` is wire-only; over-credit invariant unenforced
**Files:** `src/custodial/hcs20-reader.ts:307,579,653`; `src/scripts/verify-audit.ts` (zero hits);
`app/api/user/audit/route.ts:519-523`; `app/api/admin/audit/route.ts:631-635`;
`app/api/admin/monitoring/route.ts` (zero hits).
**Evidence:** Repo-wide grep for `refundsDroppedEmptyOriginal` returns 8 hits — 3 in the reader
(declare/init/increment), 3 in the manifest + behavioral test (assert existence), 0 in any
consumer. The user/admin audit routes destructure exactly `{ v1Messages, v2Messages, unknownMessages }`
out of `parsed.stats` and discard everything else. R10-FG-3's stated bug (over-credit because
reducers cannot distinguish a dropped refund) is **not closed by the counter** — the reducers
still cannot distinguish it because they never read it. The manifest entry at
`audit-coverage.json:669` claims "consumers (verify-audit, monitoring panel, ops dashboard)" —
none of those three exist. This is the inverse failure of pre-Phase-8: pre-fix the counter
didn't exist; post-fix it exists and nobody listens. Conservation invariant 3 still violated
on every topic with a legacy empty-`originalDepositTxId` refund.

### `[ ]` R11-P5-002 (H) — Aggregate `ledgerBalance` formula stale (R10-FG-9 still OPEN)
**File:** `src/scripts/verify-audit.ts:1376-1377`.
**Evidence:** The aggregate is `dep - rake - spent - withdrawn - refunded` — pre-Phase-6
formula. The per-token loop at lines 1392-1402 correctly subtracts `held` and `flushOrphaned`.
Phase-8 was R10-FG-1..4 only; R10-FG-9 was deferred. JSON consumers reading
`ledgerBalance` (top-level scalar) see numbers that disagree with the per-token sum. The
docstring at `verify-audit.ts:201` (`/** Derived: deposited - rake - spent - withdrawn -
refunded. */`) is also stale and reinforces the wrong contract.

### `[ ]` R11-P5-003 (H) — `heldByToken` never decremented on `prize_recovery` (R10-FG-16 still OPEN)
**Files:** `src/scripts/verify-audit.ts:865,922`; `hcs20-reader.ts:706-712`.
**Evidence:** Line 865 increments `heldByToken[r.token]` on
`play_uncertain_success_pending_triage`. Line 922 explicitly says `// deploy/prize_recovery/unknown
not credited per-user` — meaning `prize_recovery` events skip per-user reduction entirely. After
operator-initiated `recover-stuck-prizes`, the reservation is on-chain resolved but verify-audit
keeps subtracting it from balance forever. The R9-P12-005 `user_balance_negative` critical
alert at `verify-audit.ts:1413-1426` will fire on benign post-recovery state. Phase-8 did not
touch this path.

### `[ ]` R11-P5-004 (H) — `heldByToken` also not decremented on `force_release` / `force_release_override`
**File:** `src/scripts/verify-audit.ts:836-841,830-834`.
**Evidence:** The same archetype as R11-P5-003. Two control events explicitly RELEASE held
reservations (operator overrode the verifier or force-released the row). Verify-audit only
emits an alert string — no symmetric decrement of the prior `play_uncertain_success_pending_triage`'s
`heldByToken` contribution. Conservation invariant 3 over-counts hold by every released
reservation indefinitely.

### `[ ]` R11-P5-005 (H) — Behavioral test asserts signal existence, not balance-correctness invariant
**File:** `src/__tests__/r10-fg-3-behavioral.test.ts:96-107`.
**Evidence:** The test passes if `stats.refundsDroppedEmptyOriginal > 0`. It does NOT call
verify-audit's reducer or assert that the reconstructed user balance is correct in the
presence of a dropped refund. Removing the entire counter consumer chain (which doesn't exist)
would not flip this test. The test is structurally identical to R6-FG-7 / R8-FG-24 wire-only
tests that the dissection doc explicitly flagged: "the data is captured but never used; the
test asserts capture, not consumption."

### `[ ]` R11-P5-006 (H) — Schema doc silent on reader-stats shape
**File:** `docs/hcs20-v2-schema.md` (zero hits for `stats`, `refundsDropped`, `schemaValidationFailures`).
**Evidence:** The schema doc is the contract for external auditors building a fresh reader.
It documents wire fields but says nothing about `AuditReaderResult.stats`. New stat fields
(`refundsDroppedEmptyOriginal`, `schemaValidationFailures`, `agentSeqDuplicates`,
`agentSeqGaps`, `skippedMessages`) ship without doc updates. An auditor writing a conforming
reader from the doc alone would emit zero of these counters and the operator's monitoring
playbook (when one finally lands) would be unimplementable on a fresh reader. Per the project's
own "docs are the spec" principle (recorded in user memory), the doc should be the contract.

### `[ ]` R11-P5-007 (M) — Per-token `ledgerBalanceByToken` rounds to 4 decimals; aggregate doesn't
**File:** `src/scripts/verify-audit.ts:1377,1402`.
**Evidence:** Per-token balances are `Math.round(balance * 10000) / 10000`. Aggregate
`ledgerBalance` is the raw subtraction result. A user with five tokens each rounding -0.00004
to -0.0000 produces an aggregate of -0.0002 that escapes the per-token negative-balance alert
(line 1415: `bal < -1e-9` per token only). Already raised by R10-P12-009 medium; combined with
R11-P5-002 it makes the aggregate a worse signal still.

### `[ ]` R11-P5-008 (M) — `tokenReservations` shape coercion silently drops malformed entries
**File:** `src/custodial/hcs20-reader.ts:767-776`; `src/scripts/verify-audit.ts:864-866`.
**Evidence:** Reader's filter accepts only objects with string token + number amount. A
malformed reservation (token as number, amount as string) is silently dropped. Verify-audit
then reduces zero held amount and the dispatcher emits the alert with the *coerced* (truncated)
list. No counter records the drop. Same archetype family as R11-P5-001 — silent narrowing.

### `[ ]` R11-P5-009 (M) — `totalRakeReversedByToken` populated but never reduced into ledgerBalance
**File:** `src/scripts/verify-audit.ts:233`; ledger formula at 1377/1400.
**Evidence:** Field exists on `PerUserLedger` (line 233), populated from refund events'
`rakeReversed`, but neither the aggregate (1377) nor the per-token (1400) formula references
it. If a refund's `rakeReversed` should net out the user's `totalRake` (operator returns rake
when refund happens), the user balance is short by that amount. If it shouldn't (refund
doesn't reverse rake; operator absorbs), the field is dead code on the per-user ledger and
should be removed to avoid the next round confusing wire-only with consumed. Either way it's
the same Phase-6 archetype.

### `[ ]` R11-P5-010 (L) — `unknownMessages` and `skippedMessages` collapsed at the API boundary
**Files:** `app/api/user/audit/route.ts:519-523`; `app/api/admin/audit/route.ts:631-635`.
**Evidence:** The user/admin audit API surfaces `unknownMessages` to the dashboard but not
`skippedMessages` (which collapses 9+ distinct skip reasons including the new
`refundsDroppedEmptyOriginal` parent counter, dedup hits, duplicate refundTxIds, missing
sessionId). External operators reading the audit API see "everything is fine" while the topic
contains dropped refunds, dedup'd duplicates, etc. Even fixing R11-P5-001 by wiring the
counter into the API would not surface it under the current shape — the routes need to expose
the full `stats` object.

## Convergence note

Phase-8 closed the four named R10 criticals at their named sites. Cluster B in particular
followed the structural-fix discipline: counter declared, dispatcher branch added, behavioral
test authored. **But the test was authored to assert the existence of the signal, and no
consumer was wired.** This is exactly the Phase-6 archetype (`heldByToken` accumulator added
but per-token formula not updated) that R10-FG-9 / R10-FG-16 themselves recorded, recurring at
a different layer of the stack. The dissection's "tests catch prior-round archetypes, not
current-round introduction archetypes" hypothesis is empirically true for Cluster B.

**Recommended Phase-9 R11 ordering:** wire `refundsDroppedEmptyOriginal` into verify-audit's
alert array (mirror `schemaValidationFailures` pattern at `verify-audit.ts:1296-1304`) AND
into the user/admin audit route response shape; close R10-FG-9 + R10-FG-16; backfill
schema-doc `stats` shape; convert `r10-fg-3-behavioral.test.ts` from existence-assertion to
balance-conservation invariant assertion.

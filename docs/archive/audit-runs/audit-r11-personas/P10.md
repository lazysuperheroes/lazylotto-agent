## Findings

### P10-001 (critical) — `stats.refundsDroppedEmptyOriginal` has zero consumers; verify-audit, monitoring, audit routes all silently drop the field
**Site:** `src/scripts/verify-audit.ts:382` (stats print loop), `app/api/admin/audit/route.ts:631-634`, `app/api/admin/monitoring/route.ts:243-244`, `app/api/user/audit/route.ts:520-522`
**Bug:** Phase-8 Cluster B added `AuditReaderResult.stats.refundsDroppedEmptyOriginal: number` with the explicit promise (field docstring at `hcs20-reader.ts:289-307`) that "verify-audit, monitoring panel, ops dashboard" get a "recoverable signal" of dropped refund anchors. Grep for the field name across the entire repo finds NO consumer:
- `verify-audit.ts:378-396` enumerates v1Messages/v2Messages/unknownMessages/skippedMessages/sessionsByStatus/agentSeqGaps/agentSeqDuplicates and stops; `refundsDroppedEmptyOriginal` is never printed nor used to raise an alert.
- `app/api/admin/audit/route.ts:631-634` and `app/api/admin/monitoring/route.ts:243-244` and `app/api/user/audit/route.ts:520-522` selectively destructure exactly `v1Messages`, `v2Messages`, `unknownMessages` from `parsed.stats` into the response — `JSON.stringify` would have surfaced the new field automatically, but the explicit object literal swallows it silently.
**Why:** This is the textbook wire-only-closure archetype the dissection doc Section 6 predicts. The Phase-8 commit message claims the categorized counter "lets verify-audit / monitoring distinguish a dropped refund from other skips" — none of those consumers actually read it. The recoverable signal is recoverable in name only; an attacker injecting empty-`originalDepositTxId` refunds (the very forge case the field was added to detect) leaves the operator dashboards reporting "all clear". Same shape as R8-FG-* and R9-FG-* (heldByToken, flushOrphan, schemaValidationFailures).

### P10-002 (critical) — `parseRefund` has 5 null-return reasons; only 1 increments the categorized counter, rest fall into `skippedMessages` catch-all
**Site:** `src/custodial/hcs20-reader.ts:1573-1574` (parser), `src/custodial/hcs20-reader.ts:644-654` (dispatcher)
**Bug:** Parser returns null at L1573 (`!originalDepositTxId`), L1574 (`!from`, `!to`, `!Number.isFinite(amt)`, `!refundTxId`). The dispatcher at L651-653 only categorizes the empty-`originalDepositTxId` branch:
```ts
const orig = String(msg.payload.originalDepositTxId ?? '');
if (!orig) {
  stats.refundsDroppedEmptyOriginal++;
}
```
A refund with valid `originalDepositTxId` but missing `from` (the more likely attacker injection pattern, since the original-tx-id field is the only one with a writer-strict gate) returns null, increments only `skippedMessages`, and is indistinguishable from a benign duplicate-anchor skip.
**Why:** The Phase-8 closure tightened ONE of FIVE drop reasons. The catch-all `skippedMessages++` continues to absorb the other four, with the same over-credit signature that motivated R10-FG-3 in the first place. Same archetype: the comment at L646-650 says "categorize the null-drop"; the code categorizes 1/5 of the null-drops. Comment-vs-code mismatch reasserted at the same site Phase-8 just fixed.

### P10-003 (high) — `coverageStrategy: 'documentation-only'` is the renamed loophole; gate accepts `tests:[]` plus an opt-in keyword
**Site:** `src/__tests__/audit-coverage-scan.ts:80-86`, `src/__tests__/audit-coverage.test.ts:128-129, 178-193`, `src/__tests__/r10-fg-4-behavioral.test.ts:35`
**Bug:** Phase-8 Cluster A's R10-FG-4 gate (audit-coverage.test.ts:178-193) requires `coverageStrategy:'individual' && tests.length === 0` to be EMPTY. The escape hatch: the same shape with `coverageStrategy:'documentation-only'` is allowed (L129 `if (f.coverageStrategy === 'documentation-only') continue;`). The Phase-8 commit message acknowledges this — 9 R9-FG entries were "downgraded individual->documentation-only with a Phase-8 sweep note". The schema docstring at `audit-coverage-scan.ts:80-81` says documentation-only "exists for record-keeping only; no locking test at all" — but a critical/high finding marked documentation-only is functionally identical to the pre-Phase-8 placebo: zero behavioral coverage with no gate forcing the author to author a test. The gate just requires the author to opt in by typing a different string.
**Why:** The dissection doc Section 5a tightens "every critical|high MUST declare at least one test" — but the gate at audit-coverage.test.ts has no severity check. A future R11 critical can ship with `coverageStrategy:'documentation-only'` and pass every test. R10-FG-4's gate locks against ACCIDENTAL placebo (forgot to add tests); INTENTIONAL placebo (set the enum to documentation-only) is an unprotected loophole. Verifies the dissection doc Section 6 prediction: "invariants the author never wrote down" — Section 5a's severity rule is named in prose, never enforced in code.

### P10-004 (high) — Section 5b "comment->test->code lockstep" is unimplemented prose; no pre-merge scan, no CI hook
**Site:** `docs/audit-cycle-dissection-2026-05-09.md:69-73` (claims), `src/__tests__/audit-coverage.test.ts` (no scan), `.github/` (no workflow file enforces it), `package.json` (no `lint:lockstep` script)
**Bug:** Section 5b claims: "When a fix's diff includes a code comment containing `must|MUST|NEVER|do NOT|don't`, the same diff MUST add a test referencing the same finding ID. Enforced by a pre-merge scan; failures point at the comment line and demand a paired test." Grepping the repo for any tooling that scans for `must|MUST|NEVER` in diffs and cross-checks against test additions returns zero hits. The Phase-8 commits add no script, no workflow, no test that performs this scan. The dissection's "lockstep validation" (Section 5b para 3) is asserted as Phase-8 process — the process change is purely aspirational.
**Why:** This is the structural counterpart to P10-003 — invariant-in-comments-only. Phase-8 ships with a written discipline that no automated check enforces. The next round's introduction archetype (per Section 6) is exactly this shape: invariants encoded only in prose. The dissection doc warns about this archetype while *committing it in the same diff*. The Phase-8 success criterion (Section 7: "R11 lands <15 findings") cannot honestly claim convergence if the named gate is not running.

### P10-005 (medium) — `responseBalances` pattern not applied to admin/overview, public/stats, withdraw, play; same mutation hazard returns if ANY future code path reassigns `user.balances`
**Site:** `app/api/admin/overview/route.ts:67-73`, `app/api/public/stats/route.ts:54-58`, `app/api/user/withdraw/route.ts:161`, `app/api/user/play/route.ts:147`, `app/api/admin/users/route.ts:57`
**Bug:** R10-FG-2 fixed the user-status route by introducing `responseBalances` and treating `user.balances` as read-only. The fix is local to that single route. Other routes still hold live store references and read `user.balances` directly:
- `admin/overview/route.ts:67-73` iterates `user.balances.tokens` to aggregate per-token totals — read-only today, but the next contributor adding a "subtract pending" decoration would land R10-FG-2 again at a different file.
- `withdraw/route.ts:161` and `play/route.ts:147` return `refreshed?.balances ?? user.balances` — currently safe because they don't mutate, but the pattern doesn't prevent a future mutation.
- The behavioral test `r10-fg-2-behavioral.test.ts:22-29` is a "verbatim copy of the route logic"; it locks the *one* route, not the *invariant* that store-cached objects are immutable.
**Why:** R10-FG-2 fixed a symptom, not the contract. The store-cached `UserAccount` type at `src/custodial/types.ts` is a mutable object reference. There is no `Readonly<UserAccount>` return type on `store.getUser`, no `Object.freeze` at the cache boundary, no test that asserts other routes don't mutate. The Phase-8 fix relies on every future route author remembering "don't mutate user.balances" — the same author-memory gap that produced R10-FG-2. The architectural fix is to return `Readonly<UserAccount>` from `store.getUser` (or `Object.freeze` the cached value); the surgical route fix doesn't address the type contract.

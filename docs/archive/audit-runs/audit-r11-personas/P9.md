## New introductions by Phase-8

### P9-001 (severity: HIGH) — Phase-8 SADD-before-flush + withUserLock interaction can silent-commit a debit without applied-set anchor

**Sites:** `src/custodial/pendingLedger.ts:311-318` (eager) interacting with `src/lib/locks.ts:172-197`.

**Behavioral invariant violated:** "if the SADD anchor fails to record, the in-memory `updateBalance` mutation must NOT reach persisted state without retry."

**Mechanism:**
1. `withUserLock` calls `store.refreshUser(userId)` then `applyPendingLedgerForUser(store, userId)`.
2. Inside the fenced body, `store.updateBalance` mutates the live cache (live=90).
3. `await redis.sadd(...)` throws (transient Upstash failure / Lambda kill).
4. fencedClaim's catch releases the fence; `applyPendingLedgerForUser`'s outer try logs and continues.
5. Control returns to `withUserLock`, which runs `fn()` (the user's withdraw or play).
6. `fn()` completes; `withUserLock` calls `await store.flush()` at line 197.
7. **The flush commits the debited live cache to persisted state.** Applied-set entry was never written.
8. Lock released. Next drain on a different Lambda: `refreshUser` pulls persisted (debited) state; SISMEMBER on applied-set returns 0; the body **re-applies the debit → DOUBLE-DEBIT**.

**Why the test doesn't catch it:** `r10-fg-1-behavioral.test.ts` calls `applyPendingLedgerForUser` directly without simulating `withUserLock`'s post-body `store.flush()`. It then explicitly calls `store.refreshUser` to reset the in-memory mutation. Production sequence has no such reset.

**Severity:** HIGH not CRITICAL — only fires on Redis SADD failure (rare), and Phase-8's own commit message at `f3a0431` explicitly accepts a "silent loss" trade for the analogous flush-throw branch. But the SADD-throw branch was claimed clean ("body propagates → fencedClaim's catch releases the fence → next drain runs the body cleanly"); the comment overlooks the surrounding withUserLock.flush call.

**Fix sketch:** either (a) have fencedClaim's release path also signal `applyPendingLedgerForUser` to roll back the in-memory mutation (call `store.refreshUser(entry.userId)` after release), or (b) move the `updateBalance` after the SADD so a SADD throw aborts before any in-memory mutation. Option (b) is safer and a one-line move.

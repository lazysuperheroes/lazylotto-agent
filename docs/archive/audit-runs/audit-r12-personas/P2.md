### P2-002 — velocity DECRBY rollback: rollback is non-atomic but the residual exposure is bounded (LOW)

**Severity:** Low | **Triage:** quality

`MultiUserAgent.ts:2573-2585`: INCRBY then `if (proposed > cap) await redis.incrby(key, -amount).catch(() => 0)`. Between INCRBY and the conditional DECRBY, a concurrent **legitimate** withdraw observing `proposed=cap+1` would also trip over-cap and refuse. The window is ~1ms (single Redis RTT). No atomic compare-and-decrement primitive exists on Upstash, so this is the best we can do without Lua/EVAL. **Residual exposure:** an attacker pinning concurrent over-cap retries to a victim could create a 1-RTT window where one legitimate withdraw also bounces; the legitimate user retries and succeeds. This is a brief denial-of-service, not the 24h lockout R10-FG-12 closed. **Strike for shipping.** If R12+ resurfaces, migrate to a Lua script doing INCRBY+CHECK+DECRBY atomically. The `.catch(() => 0)` swallow is correct (rollback failure mid-rare-Redis-blip leaves counter inflated; the existing TTL refresh recovers in 24h, identical to pre-Phase-9 behavior).

### P2-003 — composeBalanceResponse: no cross-tenant leakage path identified (verification)

**Severity:** N/A (verification pass) | **Triage:** verified

`composeBalances.ts` filters `allPending` by `p.userId === user.userId` before merging. The four routes each authenticate via `requireTier` and resolve `user` via `getUserByAccountId(auth.accountId)` (status, check-deposits, play, withdraw) BEFORE calling the helper. There is no codepath where a route hands a different user's `Readonly<UserAccount>` to the helper. `pendingAdjustments[]` only contains entries matching the requested user's `userId`. The helper does not mutate the store-cached user (Phase-9 Cluster C's `Readonly<UserAccount>` typing enforces this at compile time). **No cross-tenant info-leak under any concurrency scenario.** The `try/catch` swallow on `listPendingLedgerAdjustments()` failure returns raw `user.balances` — informationally degraded, not cross-tenant.

### P2-004 — pendingLedger SADD-before-mutation: forge-applied attack path closed (verification)

**Severity:** N/A (verification pass) | **Triage:** verified

`pendingLedger.ts:303` (eager) and `:497` (periodic) SADD before `updateBalance`. The reasoning in the code comments (lines 273-302) correctly identifies the only branch where SADD lands but mutation never persists: **flush-throw after SADD+updateBalance**. In that case the in-memory cache is dirty, but `withUserLock`'s outer flush at locks.ts:197 catches up the persisted state, AND the next drain SISMEMBER=1 short-circuits without re-applying. **Could an attacker forge a "this was already applied" state?** Only by writing to `KEY_PREFIX.pendingLedgerAppliedSet` directly in Redis, which requires Redis credential compromise — outside the threat model (operator already controls all custodial state under that scenario). The `(userId, sourceTx)` keying ensures an attacker cannot cross-pollinate between users by replaying their own sourceTx — `sourceTx` is the on-chain refund tx, attacker-immutable. **Closed correctly.**

### P2-005 — verify.ts: route handler echoes `err.message` to client without redaction (LOW)

**Severity:** Low | **Triage:** quality (defense-in-depth)

`app/api/auth/verify/route.ts:54-60`: catch returns `NextResponse.json({ error: message }, { status: 400 })` where `message = err.message`. Post-Phase-9, the client now receives distinct strings: "Challenge expired or already used", "Challenge was issued for a different account", "Signature verification failed", "Failed to decode SignatureMap: ...". This is an information disclosure differential (account-mismatch ≠ sig-fail ≠ expired), enabling an attacker to probe whether a specific challengeId was issued for a specific accountId. The pre-Phase-9 behavior had the same leak. **Not a Phase-9 regression.** Recommend (post-ship): collapse all `SignatureValidationError` paths to a single client-facing string ("Authentication failed") and log the typed message server-side only. Triage: **process** — track for a future hardening pass; not load-bearing.

### P2-006 — pendingLedger: LLEN short-circuit cannot be exploited to suppress drains (LOW)

**Severity:** Low | **Triage:** verified

`pendingLedger.ts:114, 197, 429`: `LLEN===0` returns early. Could an attacker who can write to Redis suppress drains by deleting LIST entries? Yes — but they'd already have control of the queue contents. The LLEN short-circuit is observed AFTER `acquireUserLock` (periodic) or under the existing user lock (eager), and any `RPUSH` from `queuePendingLedgerAdjustment` lands BEFORE `LLEN` is observed by the next call (RPUSH is atomic). **No new attack path.** The `.catch(() => 0)` on LLEN means a Redis blip masquerades as empty queue → drain skipped — but the row is still queued, the next call retries. Worst case: brief drain delay during transient Redis failure, identical pre-Phase-9 hazard.

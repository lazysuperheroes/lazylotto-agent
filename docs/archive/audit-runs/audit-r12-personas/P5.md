## `[ ]` R12-P5-001 (CRITICAL) — `force_release` writer drops `userId` + `tokenReservations`; heldByToken decrement is dead code on production topics

**Triage tag:** bug

**File:** `app/api/admin/uncertain-tx/[id]/force-release/route.ts:427-434`

**Evidence:** The only production writer of the `force_release` control event:

```ts
await accounting.recordControlEvent('force_release', {
  by: auth.accountId,
  reason,
  uncertainTxId: id,
  kind: entry.kind,
  mirrorResult,
  idempotencyKey: `force-release:${id}:${fenceTs}`,
});
```

No `userId`. No `tokenReservations`. Compare to `handlers.ts:807` (`play_uncertain_success_pending_triage`) which correctly threads `userId: details.userId, tokenReservations: details.tokenReservations`.

The Phase-9 Cluster B fix at `verify-audit.ts:874-884` is gated by:

```ts
if (event.userId && event.tokenReservations) { ... }
```

On every real `force_release` anchor produced today, that guard is false. `heldByToken` is **never** decremented. The R10-FG-16 false-positive `user_balance_negative` alert that Phase-9 was supposed to kill still fires the moment any operator force-releases a triaged play.

**Synthetic trace (the one in the prompt):** seq=1 `play_uncertain_success_pending_triage` with `tokenReservations=[{token:'HBAR',amount:50}]` — held becomes `{HBAR:50}`. seq=2 `force_release` (current production shape: `{by, reason, uncertainTxId, kind, mirrorResult, idempotencyKey}`) — guard fails, held stays at 50. Aggregate `ledgerBalance = dep − rk − sp − wd − rf − 50 − 0`. As soon as `dep < 50`, `user_balance_negative` fires false-positive. Phase-9 closure is decorative.

**Fix:** route.ts:427 must pass `userId` and `tokenReservations` (read from the dead-letter entry's `details`). Also surface as a regression test: a synthetic topic with the exact two-event sequence must end with `heldByToken['HBAR'] === 0`. Phase-9 shipped no such test (the commit body explicitly says "verify-audit reduction is not exported (not unit-testable without refactor)" — that is exactly the deferral that allowed this to ship broken).

## `[ ]` R12-P5-003 (HIGH) — `prize_recovery` deferral is honest but the load-bearing risk is misstated in the commit body

**Triage tag:** process

**Evidence:** Commit body says "prize_recovery's relationship to heldByToken (P5-003 / R11-P5-003) is more nuanced than force_release; deferred." Tracing the reader: `prize_recovery` events fire from `recover-stuck-prizes.ts` AFTER a `closed_success_with_prizeTransfer.outcome='failed'` session has already settled the user's spent and credited the operator's rake. The reader's post-process at `hcs20-reader.ts:983-994` flips `prizeTransfer.status` from `failed` → `recovered` on affected sessions. **It does not touch heldByToken** because `prize_recovery` does not interact with reservations — held funds were already released at session close.

The load-bearing case the commit body hints at *does not exist*: there is no topic shape where `prize_recovery` causes a `user_balance_negative` false-positive via `heldByToken`. The deferral is honest but the *reason* for the deferral as written is not. The actual gap is that `prize_recovery` is excluded from the per-user reduction at `verify-audit.ts:965` ("`// deploy/prize_recovery/unknown not credited per-user`") which is correct for prize delivery (informational, not balance-affecting) — but warrants an explicit comment justifying the exclusion rather than treating it as a deferral.

**Fix:** rewrite the commit body's deferral justification or, in lieu of editing history, add the rationale as a comment block at `verify-audit.ts:965`.

## `[ ]` R12-P5-004 (MEDIUM) — `docs/hcs20-v2-schema.md` documents zero stats fields; external auditors cannot consume the new counters

**Triage tag:** quality

**Evidence:** `grep -n 'refundsDropped\|stats\.\|schemaValidationFailures\|agentSeqDuplicates' docs/hcs20-v2-schema.md` → **zero hits**. The schema doc is the external-auditor wire spec (per CLAUDE.md "self-sufficient — external auditors can reconstruct from the topic alone"). It documents wire payloads but nothing about `AuditReaderResult.stats` — including the four Phase-9 counters (`refundsDroppedEmptyOriginal`, `refundsDroppedMissingParty`, `refundsDroppedInvalidAmt`, `refundsDroppedMissingRefundTx`). An external auditor running their own reducer cannot replicate the over-credit guard because they cannot see what the canonical reader categorizes.

The R11 P5 finding flagged this same gap pre-Phase-9; the gap survived the Phase-9 close. Schema-doc updates are explicitly listed in the Cluster B commit body ("PerUserLedger.ledgerBalance docstring updated in lockstep") — but that is the in-code docstring, not the wire-spec doc.

**Fix:** add a `## Reader Stats Counters` section to `docs/hcs20-v2-schema.md` enumerating the dropped-refund family, `schemaValidationFailures`, `agentSeqGaps`, `agentSeqDuplicates` with the invariant each enforces.

## `[ ]` R12-P5-005 (LOW) — aggregate `ledgerBalance` formula is correct but vulnerable to drift on token-set asymmetry

**Triage tag:** quality

**Evidence:** `verify-audit.ts:1452-1459` computes the aggregate as a sum-of-values across `heldByToken` and `depositCreditFlushOrphanedByToken`. The per-token loop at 1462-1485 uses the union of six token-keyed maps. **They will agree numerically** — both sum the same per-token values — so R10-FG-9 is closed at the formula level. However: any future scalar accumulator added to `PerUserLedger` that is not also added to *both* the aggregate-side `Object.values().reduce` and the per-token `allTokens` set will silently drift them apart again. This is the exact archetype that produced R10-FG-9 in the first place.

**Fix:** extract a single `function deriveBalance(led)` returning `{ aggregate, byToken }` so both come from one source. Trivial refactor; closes the regression archetype.

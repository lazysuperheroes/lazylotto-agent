## P10-001 — `MultiUserAgent.playForUser` re-saves stale `user` AFTER `lastPlayedAt` update [CRITICAL / bug]

**File:** `src/custodial/MultiUserAgent.ts:736` then `:874`.

Cluster C correctly replaced the `user.lastPlayedAt = ...` mutation at line 736 with `saveUser({...user, lastPlayedAt: new Date().toISOString()})`. But line 874, in the same `playForUser` body, then calls `this.store.saveUser(user)` — passing the ORIGINAL `Readonly<UserAccount>` snapshot bound at line 534. That second write OVERWRITES the cache entry just persisted at line 736, reverting `lastPlayedAt` to its pre-play value.

`saveUser(user: UserAccount)` accepts a Readonly via TS structural subtyping — no compile error caught it. The Phase-9 commit body claims "Both replaced with saveUser of fresh objects" but the second saveUser at line 874 is unchanged. **This is the §6 archetype #3 (cluster-fix scope-creep with one site silently regressing) — exactly what the pre-mortem predicted.**

**User-visible failure:** every successful play resets the user's `lastPlayedAt` indicator on the dashboard. Activity tracking, idle-disconnect, and strategy-cooldown logic that reads `lastPlayedAt` see a wrong value. Observable in `r10-fg-2-behavioral.test.ts` only if it asserted post-play `lastPlayedAt`; it doesn't.

## P10-002 — `IStore.getOperator()` is mutable; sibling archetype to R10-FG-2 NOT closed [HIGH / bug]

**File:** `src/custodial/IStore.ts:152`.

The Cluster C migration made `getUser*` return `Readonly<UserAccount>` to catch top-level mutation of the store cache. But `getOperator(): OperatorState` was left mutable. `MultiUserAgent.getStatus()` (line 2046) returns `operator: this.store.getOperator()` directly into a payload that flows through `app/api/admin/overview` (line 58) and `MCP` status surfaces. Any caller doing `op.balances[token] = ...` mutates the live `RedisStore.operator` cache (RedisStore.ts:566 returns `this.operator` by reference, no clone).

This is the §6 archetype "architectural inconsistency: did the IStore Readonly migration leave OperatorState mutable when it should match." OperatorState carries `balances`, `totalRakeCollected`, `totalGasSpent` — all balance-conservation-critical. The same archetype the migration was designed to close is preserved on the operator surface.

**Recommended fix:** `getOperator(): Readonly<OperatorState>`. Any call site that needs to mutate uses `updateOperator(updater)` (already the controlled write path).

## P10-005 — `composeBalanceResponse` returns `responseBalances === user.balances` by reference on the no-pending happy path [MEDIUM / quality]

**File:** `app/api/_lib/composeBalances.ts:76`.

When no pending entries exist, `responseBalances = user.balances` (alias). The 4 routes feed it directly to `NextResponse.json` — JSON serialization doesn't mutate, so today there is no live bug. But the `BalanceResponseView.responseBalances: UserBalances` type is mutable (NOT `Readonly<UserBalances>`), so a future caller doing `responseBalances.tokens.HBAR.available -= 1` would mutate the store cache via reference identity — defeating the entire point of the Readonly migration. The architectural contract is preserved by accident, not by the type.

**Fix (one line):** return `Readonly<UserBalances>`. Or shallow-clone unconditionally to break the alias. Pre-emptive — no live exploit path today.

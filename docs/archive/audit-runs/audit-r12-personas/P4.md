## P4-001 (M) — Triage: quality

### `flush()` after partial-mutation throw still bleeds dirty cache through `withUserLock`'s post-`fn()` flush
**Site:** `src/custodial/pendingLedger.ts:303-339` (eager) interacting with `src/lib/locks.ts:191-197`.
**Bug:** Phase-9 moved SADD before `updateBalance`. Good. But the comment at lines 295-300 still describes the residual `updateBalance`-throws-after-SADD path as benign because "next drain SISMEMBER=1 → already-applied → no re-debit." This is correct for the *queue replay* path. It is NOT correct for the dirty live path. Trace:
1. SADD ok → applied-set anchor set.
2. `updateBalance` callback throws (e.g. `tokens[k]` unexpectedly absent and updater bug). The Map mutator on line 314-319 does in-place mutation; a throw mid-mutation can leave a partial decrement in the live cache.
3. `fencedClaim` releases on non-preserve throw → outer try/catch logs and continues.
4. `withUserLock` line 191 enters `await fn()`. `fn()` reads the dirty live (partial debit applied).
5. Line 197 `await store.flush()` writes the partially-decremented balance to persisted Redis. Anchor protects against re-debit, but the flushed value reflects an *uncommitted* decrement that no audit row anchors.
**Why M not H:** the in-place `Math.max(0, ...)` is a single arithmetic step on a primitive — realistically atomic in V8 for `number`. The hazard is theoretical given current `tokens[k]` shape but breaks the moment `updateBalance`'s body grows multi-step. Comment dismisses it as "lesser evil"; the lesser evil should be tested, not narrated.
**Fix sketch:** wrap the body's `updateBalance` in a try/catch that calls `store.refreshUser(entry.userId)` on throw to revert local mutation, OR have the catch at `locks.ts:182-189` re-call `refreshUser` before entering `fn()`.

## P4-002 (M) — Triage: bug

### `withUserLock` swallow-and-continue on `applyPendingLedgerForUser` throw bypasses Phase-9 anchor when error originates BEFORE SADD
**Site:** `src/lib/locks.ts:177-189`, `src/custodial/pendingLedger.ts:189-198`.
**Bug:** Phase-9's invariant ("SADD throws → no in-memory mutation → clean replay") only holds when control reaches the SADD line. The function has earlier exit/throw points: `getRedis()` failure (line 189-192 returns clean), but a `redis.llen()` reject path is `.catch(() => 0)` only — a synchronous throw from Upstash client wrapper (e.g. token-init failure that propagates synchronously) bypasses that catch. More importantly, the `lrange().catch(() => [])` on line 200-202 swallows scan failures silently → empty iteration → `withUserLock` proceeds into `fn()` with NO drain having happened. If a refund queued an entry that LRANGE silently dropped, the user can withdraw the un-debited refund. R10-FG-1 archetype recurring in the silent-empty branch.
**Why M:** Upstash REST client is reliable; the silent-`lrange`-fail branch is a rare-tail. But the swallow is the same closure-by-comment archetype Phase-8 was hit for.
**Fix:** if either `llen` or `lrange` throws/catch-swallows mid-iteration, `applyPendingLedgerForUser` should propagate to `withUserLock`'s catch and `withUserLock` should `return { lockHeld: true }` (force the caller to 409) instead of continuing into `fn()` against pre-drain state.

## P4-003 (L) — Triage: quality

### LLEN short-circuit at three call sites is correctness-safe but adds a new soft-fail mode
**Sites:** `pendingLedger.ts:114, 197, 429`.
**Analysis:** LLEN-then-LRANGE is two round-trips; a concurrent RPUSH between them lands the new entry into the LRANGE on the *current* drain. A concurrent RPUSH AFTER both reads is the next drain's problem (always was). The short-circuit `if (len === 0) return` returns BEFORE the LRANGE, so a concurrent RPUSH that lands AFTER LLEN==0 returns is missed by THIS drain — but the next drain (next withUserLock acquire, or next reconcile) picks it up. No correctness break. The new soft-fail: LLEN is `.catch(() => 0)`; under Redis flap LLEN throws, returns 0, drain returns `applied:0,failed:0`, eager drain silently no-ops while the queue actually has entries. Pre-Phase-9 the LRANGE catch had the same behaviour, so this is at worst no regression — but the comment claims "cheap behavioral close that collapses the 99th percentile call cost" without acknowledging the new failure-silently-with-pending-debits mode. `getPendingLedgerCount` (line 87) has the same shape and uses the same return value as the reconcile pass's `pendingLedgerRemaining` — a flapping LLEN reports 0 remaining when entries exist, hiding insolvency from the reconcile webhook.
**Fix:** distinguish "empty queue" from "LLEN errored" by logging a warning when `.catch` fires, and surface the error count in the reconcile response.

## P4-004 (M) — Triage: bug

### `refund.ts:915` (in-flight processRefund): `updateBalance` runs BEFORE the post-success SADD at line 1124 — same R10-FG-1 archetype Phase-9 just fixed elsewhere
**Site:** `src/hedera/refund.ts:885-993` (ledger adjust block) vs. `:1080-1135` (post-success `refundedOriginals` SADD).
**Bug:** Phase-9D's narrative says SADD must happen BEFORE in-memory mutation so a SADD-throw doesn't bleed dirty cache. In `processRefund` the order is: on-chain submit → `updateBalance` (line 915) → `updateOperator` (line 930) → `store.flush` (line 1442) → SADD `refundedOriginals` (line 1124). If SADD throws AFTER on-chain success and AFTER ledger adjust, the dead-letter + escalation fires (lines 1133-1170) — fine. But there is a separate pre-submit SADD at line 614 that lands BEFORE submit. So: pre-submit SADD lands → submit succeeds → updateBalance lands → flush lands → post-success SADD lands. The pre-submit SADD is the one that gates duplicate refunds. R10-FG-1 archetype is: *write-to-set lands, in-memory mutation also lands, flush throws → next Lambda re-applies in-memory mutation because anchor lookup-key differs from per-user-debit anchor*. Here the "anchor" is `refundedOriginals` keyed by `transactionId`; the in-memory mutation is on `user.balances` keyed by `userId`. They are NOT joined — a future `processRefund` for the same `transactionId` is gated by SISMEMBER, not by per-user state. So the residual concern is narrower: it's only the per-user-balance debit that has no idempotency anchor of its own. If `flush()` succeeds and `recordRefund` (HCS) throws, the dead-letter path fires; but if the warm Lambda dies between `updateBalance` and `flush`, the next Lambda's `processRefund` retry is gated by `refundedOriginals` SISMEMBER → refused. The user's balance was decremented in-memory only, never persisted → user keeps phantom funds equal to the refund amount.
**Why M:** the pre-submit SADD blocks the duplicate-refund window so this is "phantom credit on the user side" not "double-refund on-chain". Operator can reconstruct from HCS-20 audit + persisted state delta. But it IS the R10-FG-1 archetype landing through the `refund.ts` door, unaddressed by Phase-9D's pendingLedger-only scope.
**Fix:** wrap the `updateBalance` + `updateOperator` + `recordRefund` block in a fenced per-user-tx claim with explicit applied-set anchor (mirror pendingLedger's pattern); or move to fully-eager pendingLedger queue (queue then drain inside outer lock — same primitive).

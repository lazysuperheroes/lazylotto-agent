## P12-004 — `applyWithdrawalVelocityCap` INCRBY-then-DECRBY: correct, with one subtle hot-path concern. [BUG]
**Severity:** L (latent, not blocking ship).

`MultiUserAgent.ts:2545+` — atomic `INCRBY → check → conditional DECRBY` replaces the GET/compute/SET race. Two writers no longer undercount the cap. Good.

Subtle: the `expire(key, 24h)` call happens AFTER `INCRBY` regardless of over-cap. On the over-cap rollback path we INCRBY +amount, refresh TTL, then DECRBY. The intermediate window where the counter is over-cap is bounded by one Redis round-trip; a third concurrent caller hitting the key in that window reads the inflated value. Worst case: a legitimate caller racing an over-cap attacker sees a transient false 503. Self-heals on next call.

This is functional discipline territory: prefer `INCRBY → check → if-over { DECRBY } else { EXPIRE }` so the TTL-refresh moves to the non-rollback branch. One round-trip saved on the rollback path; one fewer transient-window race. Not a ship blocker. Fix in passing if Cluster E is reopened.

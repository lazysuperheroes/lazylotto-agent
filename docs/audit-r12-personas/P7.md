# R12 Persona P7 — Frontend / UX / API contract integrity

HEAD: 4ba4309 | Scope: R11-FG-3 closure (Phase-9 Cluster C, f1452bf).

## Verdict

Backend half is genuinely closed: all four balance-bearing routes
(`/api/user/status`, `/check-deposits`, `/play`, `/withdraw`) call
`composeBalanceResponse` and return `{ balances: responseBalances,
pendingAdjustments }`. `IStore.getUser*` returns
`Readonly<UserAccount>` (compile-time guarantee against the R10-FG-2
archetype). Dashboard merge-back paths now consume the pre-subtracted
`balances` field, so the phantom-funds view does not return.

The frontend half is incomplete — the new `pendingAdjustments` wire
field is dropped on the floor. P7-H1 from R11 stands.

## Findings (5)

### P7-H1 [HIGH, quality] `pendingAdjustments` not surfaced in UI

`composeBalanceResponse` returns `{ responseBalances,
pendingAdjustments[] }` and all four routes faithfully emit it
(`app/api/user/status/route.ts:133`, `check-deposits/route.ts:89`,
`play/route.ts:153`, `withdraw/route.ts:166`). Grep for
`pendingAdjustments` across `app/dashboard/**` returns zero hits.
The field is computed, serialized, sent over the wire, then
discarded. R11 raised this exact concern (P7-H1) and the Phase-9
commit message claims "the dashboard badge" as motivation, but no
badge was added. UX impact: a user whose available balance was
silently reduced by a queued refund debit sees the smaller number
with no explanation — looks like a bug or theft, not a pending op.

### P7-H2 [HIGH, bug] `StatusResponse` type contract missing `pendingAdjustments`

`app/dashboard/types.ts:30-45` defines `StatusResponse` with
`balances`, `velocity`, etc., but no `pendingAdjustments`. The new
field is invisible to TypeScript on every consumer:
`page.tsx:232` (`const data: StatusResponse = await res.json()`)
strips it. Even if a future PR tries to render the badge it will
fail TS compile or fall back to `any` casts. Same for the
`check-deposits`, `play`, `withdraw` response shapes (they're typed
inline in `page.tsx:403-407, 683-686, 745-753` as ad-hoc object
literals, none of which mention `pendingAdjustments`). The contract
is unenforced end-to-end.

### P7-M1 [MEDIUM, quality] Inline response types diverge from shared `StatusResponse`

`page.tsx:405, 685, 752` each carry their own slim
`{ balances?: StatusResponse['balances'] }` literal for the
play/withdraw/check-deposits responses. This is the same archetype
P3-003 / P1-002 raised against the test/route copy: any new
balance-shaped field must be added in 4+ places, and the merge-back
at `page.tsx:415-423, 690, 800` will silently miss it. Recommend a
shared `BalanceUpdateResponse` interface in `types.ts` consumed by
all four call sites and by the route handlers (via shared zod /
type), so the next field addition fails compile rather than
shipping silently.

### P7-M2 [MEDIUM, bug] Merge-back at 415/690/800 strips sibling fields

Even after Phase-9, `setStatus((prev) => ({ ...prev, balances }))`
only carries `balances` forward from the sibling-route response.
If `/play` returns `pendingAdjustments` (it does, line 153) the
field is discarded — the next dashboard read of `status` shows the
balances from `/play` but the (now stale) `pendingAdjustments` from
the original `/status` call. Same hazard for `velocity` (also
absent from `/play` and `/check-deposits` responses, so prev's
value is correctly preserved by the spread, but only by accident).
The merge logic should be a deliberate "patch known fields" map,
not a `...prev` blanket. This is the P7-C2 archetype recurrence:
sibling routes drift in shape and the merge-back creates
inconsistent client state.

### P7-L1 [LOW, process] Comment in `check-deposits` references future state

`check-deposits/route.ts:71-75` comment says "the dashboard merges
that into `setStatus({...prev, balances: data.balances})`
(page.tsx:415-423), overwriting the pre-subtracted view from
/api/user/status." Phrasing is past-tense pre-Phase-9 but reads as
present-tense to a future reader who didn't watch the audit. Add a
"(closed Phase-9 Cluster C)" suffix or move the war-story comment
to `composeBalances.ts`'s docblock (which already has it) and keep
the route comment to a one-liner referencing the helper. Cosmetic
but reduces "is this still a bug?" archaeology cost.

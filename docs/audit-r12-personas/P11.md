## P11-001 — LLEN short-circuit savings, quantified — LOW (quality)

**Site:** `src/custodial/pendingLedger.ts` L102-115, L191-202, L423-434.

**Quantification:**

- **Empty-queue path (the 99th-percentile case in steady state):** 1 LLEN round-trip (~0.3ms p50 Upstash, no payload), vs. pre-Phase-9 LRANGE 0 -1 + N JSON.parse + linear filter. With 500 cluster-wide pending entries (R11 P11-001 baseline), LRANGE alone returned ~75KB on the wire and cost ~3-5ms CPU per call. **Net win: ~3-5ms per hit on the empty path, plus ~75KB egress eliminated.**
- **Non-empty path:** 1 extra LLEN round-trip (~0.3ms RTT, payload 1 integer). LLEN is O(1) Redis-side. **Cost: ~0.3ms penalty when pending entries exist.**
- **Crossover queue size N where LLEN-cost dominates:** never. LLEN is a constant-time fixed-cost call regardless of queue length. The 0.3ms RTT is the floor cost; LRANGE on the same connection adds RTT + payload-serialize + JSON.parse, and only grows from there. Even at N=1, LLEN+LRANGE > LRANGE; the trade-off is purely on the empty-path savings.

**Crossover frequency:** if >99% of dashboard mounts hit non-empty queues (i.e., pending entries are *always* present somewhere in the cluster), Phase-9 is a net 0.3ms regression per call. With current testnet volume (pending entries clear within hours, no continuous backlog), the empty path dominates. **Watchpoint:** if pending volume becomes continuous (e.g., a withdrawal-failure storm), revisit.

**Severity:** LOW. The quantification confirms Phase-9's claim. No action.

## P11-002 — Per-user sharding deferral threshold — MEDIUM (quality)

**Context:** Phase-9 commit message states "full per-user sharding (deferred per Phase-9 dissection §7) is the structural improvement; this is the cheap behavioral close."

**Quantification of acceptable deferral window:**

LRANGE+JSON-parse cost on the non-empty path scales linearly with cluster-wide pending volume (NOT per-user volume). Each call parses ALL entries and filters by `userId`. Cost model:
- ~10µs per JSON.parse on a ~150-byte entry (V8 measured)
- Plus ~150 bytes/entry network egress

At cluster pending volume **N=2,000 entries**: ~20ms CPU + ~300KB egress per call. At N=10,000: ~100ms CPU + 1.5MB egress — Lambda cold-start budget burnt on a single dashboard mount.

**Recommended threshold for un-deferring per-user shard:** when sustained cluster-wide pending volume exceeds **~1,500 entries** (≈15ms/call CPU budget), the LLEN short-circuit no longer hides the cost — every call lands on the slow path. Add a metric on `listPendingLedgerAdjustments` non-empty-call-rate and queue-length p95; alert when p95 > 1500.

**Severity:** MEDIUM. Not a current bug, but a load-curve forecast that should be encoded as an alert before testnet→mainnet ramp.

## P11-003 — `composeBalanceResponse` allocation cost — INFO (quality, no severity)

**Site:** `app/api/_lib/composeBalances.ts` L57-104, called from 4 routes.

**Cost vs. inline:**
- Function-call overhead: ~10ns (V8 inlines after warmup).
- Closure allocation: zero. The function is a top-level export, no captured environment per call.
- Happy path (no pending): `responseBalances === user.balances` by reference — zero allocations beyond the empty `pendingAdjustments` array (~50 bytes).
- Pending path: 1 shallow clone of `UserBalances` + 1 shallow clone of `tokens` + N spread-clones of token entries. Identical to the pre-Phase-9 inline cost at `/api/user/status`; the 3 sibling routes that previously returned raw `user.balances` now pay the same allocation — but they were buggy before (R11-FG-3), so this is intentional cost.

**Net:** negligible. <1µs per call amortized. The structural win (Readonly<UserAccount> at the type contract layer) dwarfs the allocation cost.

**Severity:** INFO. No action.

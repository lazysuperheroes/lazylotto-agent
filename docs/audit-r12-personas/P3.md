## P3-001 — pendingLedger outer catch lies about its trigger; log message is a category mistake [HIGH | error]

`src/custodial/pendingLedger.ts:348-360` (and mirror at `:557-568`):

```
} catch (err) {
  // fencedClaim only rethrows on PreserveClaimError. The body
  // doesn't submit on-chain actions so this branch is impossible
  // in practice, but if it ever fires we propagate so callers
  // see the failure instead of silently corrupting the queue.
  failed++;
  logger.error('eager pending ledger apply failed (preserve-claim)', { ... });
```

The comment claims this branch is `PreserveClaim`-only and "impossible in practice." Both halves are wrong.

`fencedClaim` (`src/lib/fencedClaim.ts:162-183`) explicitly rethrows on **all** non-busy errors after releasing the fence (`throw err;` at line 182). Phase-9 Cluster D's *raison d'être* is exactly that the new bare `await redis.sadd(...)` at line 303 can throw on a Redis blip — that is the SADD-throw branch the new R11-FG-4 test exercises. So the catch is reachable, regularly, on the very failure mode Cluster D added the code to handle. The log line `'... failed (preserve-claim)'` then mis-categorizes a vanilla Redis SADD failure as a preserve-claim event. An on-call engineer searching for `preserve-claim` log entries during a Redis incident gets noise; a search for SADD failures gets nothing.

Triage: error (no incorrect user balance — the catch path correctly increments `failed++` and continues — but the operational signal is wrong, and the comment is now actively misleading future contributors who must reason about this catch when adding new mutations).

## P3-003 — Cluster C test fixture casts away the Readonly contract it was supposed to lock [MEDIUM | error]

The Cluster C closure's commit body (`f1452bf`) sells `Readonly<UserAccount>` as the load-bearing change: "catches the R10-FG-2 archetype (top-level user.balances reassignment on a store-cached reference) at compile time across all callers."

The companion test fixture `src/__tests__/r10-fg-1-behavioral.test.ts:192-220` does:

```
const store: Partial<IStore> = {
  getUser(userId: string): UserAccount | undefined { return ... ? live : undefined; },
  ...
};
return store as IStore;
```

`Partial<IStore> as IStore` strips the `Readonly<UserAccount>` return types from `getUser` and friends. The mock's `getUser` returns mutable `UserAccount`, and the test then mutates `live.balances` freely. The compile-time guarantee Cluster C purchased does not run on this test fixture — a contributor reverting `IStore.ts:142-145` from `Readonly<UserAccount>` back to `UserAccount` produces zero failures here. Plus `strategySnapshot: {} as never` (line 231 + r10-fg-2 line 114) masks the schema for the same reason.

Triage: error. Type laxity in tests masks the very migration the cluster sells.
